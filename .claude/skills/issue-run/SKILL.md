# issue を1件、通しで進める

起票済みの issue を1件選び、コミットまで進める。1回の実行で扱う issue は**1件**（1つの issue は1回のコミットで閉じられる大きさで起票してある）。手順はすべてこの会話（メイン）で行い、レビューだけは REVIEW.md で決めてあるもの（`/code-review`・`allergen-safety-reviewer`）に任せる。

複数の issue を続けて片付けるときは、このスキルではなく `issue-triage`（順番を決めてキューのファイルにする）と `issue-queue`（キューの上から1件ずつサブエージェント `issue-worker` に任せる）を使う。`issue-worker` は、このスキルの 2.〜5. の 1. を手順の正として読む。ここを直すときは、`issue-worker` の分担と食い違わないか確かめる。

ユーザーの承認は**2か所**で取る。承認なしで次へ進まない。

- **承認1**：計画とタスクを見せたあと（実装の前）
- **承認2**：確認とレビューのあと（コミットの前）。コミットはユーザーの指示があってから行う（CLAUDE.md）

## 0. 準備

- gh：Git Bash で `gh` が見つからないときは `"/c/Program Files/GitHub CLI/gh.exe"` を使う。ログインしていなければ、ユーザーに `! gh auth login` を頼む
- `git status` を見る。**この issue と関係ない変更が作業中にあれば、先にユーザーに伝える**（`precheck.py` は作業中の差分の全体を確かめて記録するので、混ざると区分もコミットも分けられない）。先にコミットするか、退避するかはユーザーが決める

## 1. トリアージ

番号を言われていれば、その issue を読んで 2. へ進む（`gh issue view <番号>`）。

言われていなければ、開いている issue を並べて選ぶ。

```
gh issue list --state open --limit 50 --json number,title,labels
```

次の順に並べ、上位3件を理由つきで見せて、ユーザーに選んでもらう。

1. `安全レビュー` が付いた `種類: 不具合`（子どもの安全に関わるもの）
2. `優先度: 必須`
3. `優先度: あると良い` → `優先度: 余裕があれば`
4. 同じ優先度の中では、締切（2026-11-08 20:00）までに終わらせやすいもの（リスクが低い・触るファイルが少ない）を先にする

ほかの issue と重なるもの（同じファイル・画面を触るもの、例：テーマとダークモード）は、まとめずに「先にやると後が楽になる方」を勧め、関係を一言添える。

## 2. 計画

issue の本文（特に**終わりの条件**と**関係する要件**）を読み、短く調べる。

- 要件：`docs/requirements/` から、関係する `FR-`・`SR-`・`NFR-`・`SC-` の受け入れ条件を読む
- コード：`src/` を grep して、触るファイルと、まねできる既存の書き方を見つける。触るファイルに合う `.claude/rules/`（`csharp.md`・`react.md`・`biz-logic.md`・`claude-api.md`）を読む
- リスク：触るファイルを REVIEW.md の「1. リスクの区分」の表に当てて決める。issue のラベルは起票のときの見込みなので、違えばそう書く。`python tools/precheck/precheck.py --dry-run` は作業中の差分で判定するので、ここではまだ使えない

**止めてユーザーに聞くとき**（計画を作る前に）：

- 要件を変える話（要件にない動き・要件と違う動き）だと分かった。特に `03-allergen-safety.md`（SR-）を緩める方向のもの
- issue の書き方では、何をすれば終わりか決められない
- 新しいプロジェクト・フォルダ・パッケージが必要になる（CLAUDE.md で、ユーザーが決めることになっている）

## 3. タスク分解

計画を、1つずつ確かめられる手順に分ける。目安は3〜7個。各タスクに「何をして、何で確かめるか」を書く。

- ロジック（Biz）を変えるなら、テストを書くタスクを入れる（xUnit。`biz-logic.md`）
- 画面を変えるなら、E2E を足すか直すタスクを入れる（`src/oyatsubiyori.client/e2e/`）
- 最後のタスクは「implementation-tasks.md の 13. の表の『状態』を更新し、`python tools/build-tasks-html/build.py` を実行する」

### 承認1

ユーザーに次のものを見せて、OK をもらう。

- issue の番号・タイトルと、終わりの条件
- 計画（方針・触るファイル・関係する要件）
- タスクの一覧
- リスクの区分（高なら、`allergen-safety-reviewer` を使うかどうかも）
- 決めていないこと・迷ったところ（あれば）

直してほしいと言われたら、計画を直してもう一度見せる。

## 4. 実装

タスクを順に進める。CLAUDE.md・`.claude/rules/` に従う（コメントと UI の文言は日本語、識別子は英語、判定と計算はクライアントに書かない、など）。

- Biz の `.cs` を編集すると、フックが xUnit を走らせる。落ちたら次のタスクへ進まずに直す
- **issue の範囲を広げない**。途中で別の直したいことに気づいたら、実装は止めずに、エージェント `issue-drafter` をバックグラウンドで呼んで案を作らせる（起票はこの issue が終わってから、ユーザーの確認を取ってメインで行う）
- 計画どおりにいかない（思ったより大きい、計画の方針が使えない）と分かったら、そこで止めて、計画を直してユーザーに伝える。黙って方針を変えない
- 最後のタスクで、`docs/implementation-tasks/implementation-tasks.md` の 13. の表のこの issue の行の「状態」を `✅ <今日の日付>`（終わった）か `🔶 <残り>`（一部だけ）にし、`python tools/build-tasks-html/build.py` を実行する。**`precheck.py` の前に**行う（確認のあとに変えると、コミットのフックが止める）

## 5. 確認とレビュー

REVIEW.md の「2. コミット前の手順」に従う。

1. **確認**：`python tools/precheck/precheck.py`（画面を変えたら E2E も自動で走る。中身が高に当たるのに区分が中と出たら `--risk high`）。出力をユーザーに見せる。E2E が走ったら、PC とスマホの画像を見る
2. **レビュー**（区分が中・高のとき）：`/code-review` で差分を見る
3. **安全レビュー**（高で、アレルゲン・献立・Claude の出力に触れるとき。`安全レビュー` のラベルが付いた issue は必ず）：エージェント `allergen-safety-reviewer` に、issue の番号と終わりの条件、変えたファイルを渡す。計画や実装のときの考えは渡さない（その考えに引っ張られずに見てもらうため）
4. **直す**：指摘は REVIEW.md の「4. 指摘の分け方」で分ける。「重要」は必ず直し、「細かい点」は直すか理由を一言書いて閉じる。直したら 1. からやり直す
5. **往復は3回まで**。2回目からは前回のレビュー後に変えた差分だけを見せる。3回で残った指摘は、ユーザーに判断を仰ぐ。同じ種類の指摘が2回出たら、`CLAUDE.md`・`.claude/rules/`・`REVIEW.md` に書き足す案を出す
6. **終わりの条件を1つずつ確かめる**。満たしていないものがあれば、状態を 🔶 にするか、実装に戻る

ログイン・HTTPS・公開の設定に触れたら、デプロイ前に `/security-review` が必要なことを伝える。職員が見て判断する文言・画面を変えたら、レビューで済ませず、ユーザーに画面を見てもらう。

### 承認2

ユーザーに次のものを見せて、コミットしてよいか聞く。

- 変えたファイルの一覧と、何をしたか（短く）
- `precheck.py` の結果、レビューの指摘とその扱い（直した／理由を書いて閉じた／残した）
- 終わりの条件それぞれの結果
- コミットメッセージの案

## 6. コミット

OK をもらってからコミットする。

- メッセージは日本語。1行目は「何をどうしたか」。本文に `Closes #<番号>` を入れる（push で issue が閉じる）
- 区分が高なら、本文に「確かめ方・リスク・戻し方」を書く（フックが止める）
- 日本語の長いメッセージは、scratchpad に Write ツールで書いて `git commit -F <ファイル>` で渡す（ヒアドキュメントは失敗しやすい）
- 末尾には、会話で指定された Co-Authored-By の行を入れる
- フックに止められたら、理由を読んで直す。フックを外して通そうとしない
- **push はユーザーに言われてから**。言われたら push し、CI（`.github/workflows/ci.yml`）の結果を確かめる。失敗したら、次の issue より先に直す

終わったら、コミットのハッシュ、閉じる issue、残したこと（🔶 の中身や、レビューで残った指摘、issue-drafter で作った案）を伝え、次の候補を1件挙げる。
