# issue のトリアージとキューのファイル

開いている issue をまとめて読み、進める順番を決めて `docs/context/issue-queue.md`（**キュー**）に書く。キューは、スキル `issue-queue` が上から1件ずつサブエージェントで片付けるときの台帳になる。このスキルは**読むことと、キューを書くことだけ**をする（コードも issue も変えない）。

- キューは手元だけで使う。`docs/context/` は `.gitignore` で除外してあるので、公開されず、`precheck.py` の差分にも混ざらない
- issue が本体で、`implementation-tasks.md` の「13. ブラッシュアップ」の表が公開の記録。キューは「順番と、その日の進み具合」を持つ作業用の紙

## 1. 集める

```
gh issue list --state open --limit 100 --json number,title,labels,body
```

- Git Bash で `gh` が見つからないときは `"/c/Program Files/GitHub CLI/gh.exe"` を使う
- キューがすでにあれば読む。`✅`・`⏭`・`⏸` の行と「記録」は**消さずに残す**（作り直すのは「待ち」の行の順番と見込みだけ）。キューにあって GitHub で閉じている issue は、状態が空なら `✅ （GitHub で閉じた）` にする
- `git status --short` を見て、作業中の差分があれば、どの issue の途中かを当てる（触っているファイルと issue の本文から）。キューの「作業中の差分」に書く

## 2. 1件ずつ見る

issue ごとに本文の「終わりの条件」「関係する要件」「リスクと確かめ方」を読み、次を決める。issue が多い（10件を超える）ときだけ、触るファイルの調べものを `Explore` エージェントに任せてよい。

| 項目 | 決め方 |
| --- | --- |
| 触るファイル（見込み） | 本文の「触りそうなファイル」を、`src/` を grep して確かめる。リスクはこのファイルで REVIEW.md の「1. リスクの区分」に当て直し、ラベルと違えば「リスク」の欄に `中→高` のように書く |
| 大きさ | S（ファイル1〜2個・1時間以内）／M（3〜5個）／L（それより大きい、または新しい API・テーブルが要る）。L は「1回のコミットで閉じられる大きさ」を超えていないかも見る。超えていれば「決めてほしいこと」に分け方の案を書く |
| 先に要る | ほかの issue を先に終えた方がよいもの。**同じファイルを触る issue は、同時に進められない**ので、必ずどちらかを先にする（例：テーマを選べるようにする → ダークモード）。「先にやると後が楽になる方」を先にする |
| 進められるか | 次のどれかに当たれば、状態を `⏸ 要相談` にし、「決めてほしいこと」に問いを書く：要件を変える話（特に SR- を緩める方向）／終わりの条件があいまいで、何をすれば終わりか決められない／新しいプロジェクト・フォルダ・パッケージが要る（CLAUDE.md でユーザーが決めることになっている） |

## 3. 並べる

上から順に、次の決まりで並べる（`issue-run` の「1. トリアージ」と同じ考え方）。

1. `安全レビュー` が付いた `種類: 不具合`（子どもの安全に関わるもの）
2. `優先度: 必須` → `あると良い` → `余裕があれば`
3. 同じ優先度の中では、大きさが小さく、リスクが低いものを先にする（締切 2026-11-08 20:00 までに1件でも多く閉じるため）
4. ただし「先に要る」は必ず守る（後ろの issue を、先に要る issue より前に置かない）
5. 作業中の差分がある issue は、いちばん上に置く（差分を片付けないと、ほかの issue を始められないため）

締切までに終わりそうにないもの（L で優先度が「余裕があれば」など）は、消さずに末尾に置き、メモに「締切後の候補」と書く。

## 4. 書く

`docs/context/issue-queue.md` を Write ツールで書く（日本語の長文は、Bash のヒアドキュメントより Write の方が確実）。形は次のとおり。`issue-queue` はこの見出しと列の名前を頼りに読み書きするので、変えない。

```markdown
# issue のキュー

最終トリアージ：2026-11-04 19:30（開いている issue：6件）

<!-- スキル issue-triage が作り、issue-queue が「状態」と「記録」を書き換える。手元だけで使う（docs/context/ は公開しない） -->

## 作業中の差分

（git status で見えた、まだコミットしていない変更と、どの issue の途中と見たか。なければ「なし」）

## キュー

| 順 | ID | タイトル | 優先度 | リスク | 安全 | 大きさ | 先に要る | 触るファイル（見込み） | 状態 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | #1 | サイドバーの選ばれた項目を… | あると良い | 低 |  | S |  | `app/layout/AppLayout.tsx`、`e2e/sc-02-layout.spec.ts` | 待ち |
| 2 | #3 | PC でもサイドバーを開閉できるようにする | あると良い | 中 |  | M | #1 | `app/layout/AppLayout.tsx` | 待ち |

状態：`待ち` / `作業中` / `⏸ <理由>` / `✅ <コミットのハッシュ>` / `⏭ 見送り（<理由>）`

## 順番の理由

- #1 → #3：どちらも `AppLayout.tsx` のサイドバーを触る。選ばれた項目の見た目を先に決めると、開閉のときの見た目を一度で決められる
- （「先に要る」と、決まり 3. の順番から外したものだけ書く）

## 決めてほしいこと

- #5：（問い。答えの候補があれば並べる。なければ「なし」）

## 記録

- 2026-11-04 19:30 トリアージ（6件）
```

- 「触るファイル」は `src/oyatsubiyori.client/src/` や `src/OyatsuBiyori.` を省いた短い形でよい
- 「記録」には1行ずつ足していく（トリアージ・着手・コミット・保留・見送り）。古い行は消さない

## 5. 伝える

キューの上から5件ほどを、順番・大きさ・先に要る issue つきで短く見せる。あわせて次を伝える。

- 「決めてほしいこと」があれば、その問い（答えをもらったら、キューのその issue を `待ち` に戻し、本文に書き足すべきことがあれば brushup-issue の流儀で issue にコメントする案を出す）
- 作業中の差分があれば、それを先に片付ける必要があること
- 進めるときは `issue-queue` で上から順に片付けられること（1件だけなら `issue-run`）
