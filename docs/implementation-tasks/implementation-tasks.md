## 11. 決まったこと

### 11.1 要件定義で決まっていること

根拠は括弧内。

#### 範囲・利用者

- 利用者は職員1人・アカウント1つ・施設1つ。職員の管理画面・新規登録は作らない（01 §3、FR-AUTH-03、Q-10）
- 子どもは登録しない。施設の「避ける品目」の一覧だけを持つ。全員が同じおやつを食べる（FR-AVOID、Q-05）。出欠は献立に反映しない（Q-13）
- 作らないもの：発注連携・栄養計算・レシピ管理・配布物・複数施設・スクレイピング（01 §5）、商品の手での登録（FR-PROD-10 欠番）、注意メモ（FR-AVOID-04 欠番）、祝日マスタ（Q-22）、店で買うおやつ（Q-21。「おやつなし」＋見出し＋週の予算を下げる）
- 優先度：必須／あると良い／余裕があれば の振り分けと、必須の作る順番（01 §5）

#### 技術・構成

- React 19 + TypeScript（Vite）、MUI・TanStack Query・react-router・notistack・dayjs、Feature-Sliced Design（react.md）
- ASP.NET Core（.NET 10）+ EF Core + SQLite、依存方向 `Server → Data / Claude → Biz`、Result 型・Repository・QueryService（csharp.md）
- テストは `src/OyatsuBiyori.Biz.Tests/`（xUnit）を1つ（D-08）
- 認証は ASP.NET Core Identity + Cookie。10回失敗で15分ロック・ログイン API は1分10回・パスワード12文字以上（種類は問わない）・初期パスワードは変更を強制・30日保持（延長あり）・Antiforgery・`/api` は 401（D-01、D-28、NFR-SEC-10）
- 日時は UTC で保存、日付の判定は日本時間（「1日」の区切りも）。Biz には `TimeProvider` を渡す（D-29、NFR-OPS-07）
- Claude を呼ぶ処理はバックグラウンドで受け付け、画面は2秒ごとに状態を取りに行く。状態はメモリ、再起動で失敗扱い（D-26）。確定前のチラシの読み取り結果はメモリに24時間（D-36）
- 画像はブラウザで JPEG・長辺 2576px・品質 0.85 に変換。PDF は pdf.js で画像にする（Claude に PDF は送らない）。1回10枚・1ファイル 20MB（D-27）。サーバーは画像を保存せず、呼び出しが終わったら破棄（NFR-SEC-06）
- 本番は XServer VPS（Windows Server）+ IIS、`oyatsu-biyori.com`、Let's Encrypt（win-acme）、API キーはサーバーの環境変数（D-06、D-07）。サーバー上でビルドしない。バックアップは1日1回以上・7世代（NFR-OPS-02）

#### Claude の使い方

- 構造化出力（JSON スキーマ）で受け、Biz で検証してから使う（D-04）
- モデルは用途ごと：照合の判定は Haiku、画像の読み取り・献立づくりは Sonnet、精度不足なら献立提案や読み取りの検証だけ Opus。モデル名は設定から（D-05、D-10、NFR-OPS-05）
- 献立案は Biz で検証し、エラーだけ Claude に返して直させる（3回まで）。警告は表示だけ（D-11、D-13、D-23）
- チラシの読み取りは2段で検証：アプリ（税込の整合・抜け・二重）と、別の呼び出しの Claude（指摘だけ）。アレルゲンは確認を増やす方向の指摘だけ採用（D-17、SR-19）
- 入れ替え案はアプリが全通り計算（1か所の入れ替え・1日に1品の追加・1か所のパック数 ±1、上位3件）。Claude は選択と説明だけ。チャットで頼まれたときもボタンと同じ案を出す（D-25、FR-MENU-26）
- 献立づくり（献立案の作成・チャットでの組み直し）は、はじめからエージェントで作る。手書きのループ・10回まで・`submit_menu` で止める（D-18・D-82）
- 費用：トークン数を毎回ログに出す。Console の月の上限とアプリの1日200回の上限の両方（D-30）

#### アレルゲン（安全）

- 29品目（特定原材料9・準ずるもの20）をマスタで持ち、「表示が確実でない」印（推奨20品目・経過措置中のカシューナッツ）を付ける。施設の追加品目と探す言葉、グループ（ナッツ類11品目・甲殻類）も初期データにする（D-22、03 §2）
- 保存するステータスは「確認済み」「参考」の2つ。記録なし＝不明。「要再確認」は表示時に求める（再確認期間は既定90日）（D-03、03 §3）
- 「含む」は有効な記録（最新の確認済みと、それより後のすべての記録）の和集合。参考の記録では減らない（D-33）
- 判定は「含む」→「探す言葉」→ ステータスの順。結果は「入れられない / 警告 / 安全」の3つ（D-19、SR-21）
- 探す言葉は商品名と全文2列（OCR と職員の修正）の両方に、同じ正規化で部分一致。当たったら取り消せない（D-21、D-35、SR-14）
- チラシの取り込みで「確認済み」の商品に「参考」を足さない。食い違いは SR-20 で扱う（D-20、D-34）。表記のない商品は「参考（表記なし）」（D-16）
- チラシのアレルゲン表記に書かれた品目は、推奨品目でも「含む」として記録する（03 §3「チラシの品目」は品目を限っておらず、03 は他の要件に優先する）
- 判定と届いた後の警告は保存せず、表示のたびに求める（D-15）。確定済みの献立で判定が警告の範囲で変わったら確定のまま「確認し直し」（D-37）
- 確定時の警告は1件ずつチェック（Q-23。試用で見直す）

#### データ・業務

- 主キーは UUID（文字列）、JAN は NULL 可・UNIQUE。アレルゲン確認は追加のみ（04 §1）
- 予算は**週ごと**。既定の週の予算を献立に写して上書きできる。月の予算・実績は持たない（D-38）
- チラシは保存しない。献立ごとに掲載品の写しを持ち、候補と価格はこれで決める（D-24）。チラシの確定は商品ごと。取り込み直すと写しを置き換える（FR-FLYER-02・06b）
- 1つの週に献立は1つ。保存の衝突は止めて知らせる。下書きは削除可、確定済みは不可（D-31）
- 再来週分を注文するため、献立一覧は今週・来週・再来週を未作成でも出す（Q-19）
- おやつの分類は しょっぱい / あまい / のどごし / 対象外 の固定値。重複は しょっぱい・あまい を30日（Q-04、Q-06）。Claude に渡すのは確定献立、「同じ商品」は product_id の一致（FR-MENU-12・33、FR-COND-06）
- 照合は 完全一致 → Dice 係数（0.3）上位5件 → 判定 → 職員が確定（D-02、D-32）
- 献立の画面のモック（menus・menu-step1〜4）は要件定義に合わせて直した。ほかのモックは直さない。食い違いは要件定義に従う（D-39、07 §4）
- ダミーデータは `samples/`。デモのチラシは架空（D-12、D-14）

### 11.3 整理の中で決めた実装上の判断

レビューで見つかった、要件で決まっていない技術的な点。どれも要件の意図の範囲で決めた。違和感があれば変える。

- 初期データの探す言葉は `allergen_keywords.is_seed` で見分ける（U-11 を実装するため）
- `EntityBase.UpdateUserId` は NULL 可（マスタのシードとシステムの処理のため）。シードは固定の Id と日時
- 施設の追加品目の削除を止める「参照」は `allergen_check_items`・`avoided_allergens`・グループ。`safety_setting_logs` は数えず、品目名を `detail` に残して `allergen_id` は外部キーにしない
- `menu_days` の日の種類・見出しにも「職員が直した」印を持つ（U-19 を人数以外でも守るため）
- U-37 の「変えない」のは献立に写す値（人数・曜日の日・週の予算）。重複の期間・補足ルールは今の設定を使う
- 過去の週のチラシの取り込みでは、商品の価格・注文番号・最後に載った週を古い値に戻さない
- 取り込み直しの写しは、その結果を最初に確定した時点で空にしてから追記する
- 入数・1人あたりの個数は1以上、税込価格は1以上の整数
- 入れ替え案で試すのは、通常の日で人数が1以上の日だけ
- 商品の「最終確認日」は最新の記録の確認日（ステータスと同じ記録）
- SDK の自動の再試行は切ってアプリで再試行する（U-27 の数え方のため）。60秒・3分は目安で、打ち切る期限はタイムアウトと再試行の合計より長くする
- DateTime の列はすべて Kind=Utc にする ValueConverter を付ける
- プロンプトは EmbeddedResource にする。IIS の上限は Server プロジェクトの web.config に書く
- 照合（Haiku）の呼び出しは、1回の取り込みでの上限を設定で持つ
- 29品目などはフロントの定数にせず API でマスタから取る（react.md の一文を直す）
- （第2回）照合で内容量が片方か両方にない商品は、名前が同じでも「同じ商品」「内容量違い」に決めず Haiku に回す（空どうしで「同じ商品」にすると、根拠なく確認を引き継ぐため。SR-05）。同じ商品の候補が2件以上（既存の商品の二重）なら、まとめて確定させない
- （第2回）チラシのアレルゲン表記は、語が品目名・探す言葉を**含めば**対応づける（乳成分・牛乳 → 乳、鶏卵 → 卵。多めに当たる方向）。対応づけできない語は記録の `source_note` に残し、取り込みの確定を止める。「なし」「－」だけの表記は「表記なし」
- （第2回）施設の追加品目に探す言葉が0件なら、読み込み忘れとして例外で止める（黙って SR-14 が効かなくなるのを防ぐ）。再確認期間が1日未満でも止める
- （第2回）有効な記録には、最新の確認済みと同じ日時の記録も含める（含むを広く取る）。未確認の品目は最新の確認済み1件だけで数える
- （第2回・安全レビュー）判定は「確認済み」の記録の前提（情報源がパッケージ・全文が読み取りか職員の確認のどちらかにある・品目の行がある）を満たさない記録があれば例外で止める。**Data で商品を読むときは `AllergenChecks` → `Items` と、品目の `Keywords` を必ず読み込む**（1つの経路にまとめる）。確認済みの記録・言葉を持つはずの品目の読み込み忘れは例外になるが、**参考の記録だけの商品で `Items` を読み忘れても Biz では検出できない**（表記なしの参考は行0件が正しいため）。Data のテストで「参考の含むが判定でエラーになる」経路を1本確かめる
- （第2回・安全レビュー）パッケージの読み取り（`AllergenExtractor`）で同一工場・コンタミの注意書きを `ContaminationNote` に写しても、原材料の全文からは消さない（全文から消すと探す言葉がかからなくなる。判定は注意書きを探さない。SR-11）
- （第2回・検証）探す言葉の正規化で、長音に似た文字（「一」「－」など）を「ー」にそろえるのは、直前の文字（空白・改行は飛ばし、読点などの記号は飛ばさない）がかなのときだけ（「ソース、一味」の「一味」を見落とさないため）
- （第2回）商品一覧の「最終確認日」（D-80：状態を決めている最新の記録の日付）は `AllergenCheckHistory.LatestDate`、最新の確認済みの日付は `LastConfirmedDate`
- （第3回）判定・検証・確定・入れ替え案・届いた後の影響の入力は `MenuContext` にまとめる。**要求のたびに作り直し**（判定を商品ごとに覚えるため、確認の記録を足したあとは必ず新しく作る。T5-06）、**献立に入っているすべての商品**を読み込む（写しの商品だけだと「掲載品にない」が「存在しない商品」になる）
- （第3回）重複は `|その日 − 出した日| ≤ 期間` を期間内（N日目まで）とする。後の週の確定献立も「○日後に出す予定」で警告し、同じ週の中は分類の期間にかかわらず両方の日に警告する。Claude に渡す確定献立は、過去は最長の期間＋7日、未来は週末から max(最長の期間, 7日)
- （第3回）Claude の案（`MenuProposal`）は日ごとの商品 ID と理由だけ。1人あたりの個数・パック数・金額はアプリ（`MenuItemFactory`）が決める。存在しない商品・掲載品にない商品・献立にない日付は商品を作らずにエラー
- （第3回）確定時の確認（`MenuConfirmationChecker.Acknowledge`）は画面から判定を受け取らず、サーバーで判定し直して記録する。入れられない商品・安全な商品の確認は受け付けない。確定ボタンの時点でも `Check` をやり直す。指紋は版の接頭辞（`v1:`）つきで、商品 Id・種類・最新の記録・最新の確認済み・避ける品目・未確認・含む・当たった言葉から作る
- （第3回）`menu_items.amount` は、金額を数える日（通常の日で人数1以上）だけ パック数 × 価格。手作り・おやつなし・人数0の日は0（その日の金額と合わせる）
- （第3回）チラシの取り込みで読めなかった価格・税抜・注文番号（null）では、商品の前の値を消さない。手順2の価格は `ApplyManualPrice` で価格だけを、取り込みと同じ週の条件で上書きする
- （第3回）要望を直したときに戻す「通常の人数」は、今は引数で受ける。**T3-02 で `menus` に通常の人数（作ったときの設定を写す）の列を足し**、それを渡す（U-37）。要望・チャットの人数は0〜1000人（`InputValidator.MaxChildrenCount`）
- （第3回・最終承認）T4-09 で `BudgetFitSearcher.Apply` に渡す案は、サーバーが持っている `Search` の結果から選ぶ（画面から送られた案の JSON をそのまま渡さない）。`Apply` は予算・実績・日・パック数・価格が案を作ったときと同じときだけ反映する
- （第3回・安全レビュー）確認の記録（T5-05）の `raw_ingredients_ocr` は画面から受け取らず、サーバーが持つ読み取り結果から入れる（SR-12・SR-14 の二重の守りのため）。反映しなかった要望の文に子どもの名前が写りうるため、要望の入力欄の「名前を書かない」案内（NFR-SEC-05a）を必ず出す
