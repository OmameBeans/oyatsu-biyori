01. 概要

1. 目的

学童保育の職員が毎週1〜2時間かけているおやつ献立づくりを短縮する。

コープのチラシを撮影（またはファイルで取り込み）するだけで、1週間分の献立案を Claude が理由つきで提案し、職員はチャットで修正を依頼できる。アレルゲンの最終確認は、必ず職員がパッケージの原材料表示を見て行う。

献立の条件は2種類に分ける。

種類内容設定のしかた
固定条件アレルギー・予算（週ごと）・人数条件設定の画面で事前に登録する。アプリが必ずチェックする
自然言語の条件その週ごとの要望（例：「しょっぱいものとゼリー系を合わせて出したい」「金曜は誕生日会なので豪華にしたい」「水曜は都民の日なので子どもが○○人」）献立を作るときに、文章で伝える

2. 背景と課題

課題内容
時間がかかるチラシを見ながら献立を考える作業に、毎週1〜2時間かかっている
条件が多いアレルギー・予算・人数に加え、行事や組み合わせなど週ごとの事情を同時に考える必要がある
気が抜けない子どもの安全に直結する作業を、保育の合間に行っている
情報が足りないチラシにはアレルゲン情報がほとんど載っていない

3. 利用者

利用者説明主な端末
職員（1人）献立を作る・商品のアレルゲンを確認する・施設の条件を設定する。開発者ではないスマホ（撮影）、PC（ファイルの取り込み・献立の確認・編集）
  • 使うのは職員1人を想定する（アカウントは1つ。職員の追加・権限の管理はしない）
  • 想定する施設は1つ（複数施設への対応はスコープ外）
  • ITに詳しくない人が、説明なしで使えることを目指す

02. 機能要件

各要件には ID を振る。実装・テスト・コミットメッセージで参照してよい。
アレルゲンに関わる要件は 03-allergen-safety.md の安全要件（SR-xx）が優先する。

1. 条件設定・固定条件（FR-COND）

優先度：必須

献立の固定条件（アレルギー・予算・人数）を事前に設定する。固定条件はアプリが必ずチェックし、Claude の判断に任せない。
あわせて、同じ商品を続けて出さないための重複ルールも設定する（アプリが警告する）。
アレルギーは「2. 避ける品目（アレルギー）の設定」で設定する。それ以外の条件は、献立を作るときに自然言語で伝える（5.1）。

ID要件
FR-COND-01通常時の子どもの人数を設定できる（現場は40〜70人程度。ダミーデータもこの規模で作る）
FR-COND-02既定の週の予算（円・税込）を設定できる。献立を作るときにその週の予算として写し、献立ごとに手で上書きできる（週の予算の扱い）
FR-COND-03おやつを出す曜日を設定できる（既定：月〜金）。献立には、この曜日の日をすべて作る。祝日はアプリで判断しない（祝日のマスタは持たない）。休みの日は、要望で伝えるか、日ごとのカードで日の種類を「おやつなし」に切り替える
FR-COND-04アレルゲンの再確認期間を設定できる（既定：90日）
FR-COND-05おやつの分類（しょっぱいもの / あまいもの / のどごしのいいもの）ごとに、同じ商品を出さない期間を設定できる（既定：しょっぱいもの・あまいもの 30日、のどごしのいいもの 設定なし）
FR-COND-06重複についての補足ルールを自然言語で設定できる（任意。例：「ポテトチップスは味違いでも同じ商品として60日あける」「ゼリーは週1回まで」）。献立を作るたびに Claude に渡す。補足ルールで FR-COND-05 の期間を短くすることはできない（アプリの警告は FR-COND-05 の期間で出す）

受け入れ条件

  • 人数・予算は1以上の整数のみ受け付け、不正な値はエラーメッセージを表示する
  • 変更した条件は、次に作る献立から反映される。作成済みの献立は、確定済みも下書きも変わらない（D-74）。変えないのは献立に写した値（人数・おやつを出す曜日の日・週の予算）で、重複の期間（FR-COND-05）と補足ルール（FR-COND-06）は、献立を作る・直すときの今の設定を使う。ただし避ける品目・探す言葉・再確認期間はアレルゲンの判定に使うため、変更はすぐに今日以降の献立の警告に反映する（03 の 5）

週の予算の扱い

予算は週ごとに持つ（2026-11-03 に月単位から変更。月の予算・月の実績は持たない）。表示は 実績 / 予算 の形にする（例：12,380円 / 12,500円）。

週の予算 = その献立の weekly_budget（作るときに既定の週の予算を写し、職員が上書きできる）
週の実績 = その週の献立の金額の合計
  • 週は月曜始まりとし、日付は日本時間で判定する（NFR-OPS-07）
  • 特定の日を豪華にする（誕生日会など）ことは許す。週の実績が予算を超える場合は警告する（確定は止めない）
  • 店で買うおやつ（誕生日会のケーキ・アイス、パン屋のパンなど）はアプリで扱わない。その日は日の種類を「おやつなし」にして見出し（例：「誕生日会（ケーキ）」）を付け、その代金の分だけ週の予算を手で下げる（Q-21）
  • 予算が余ったとき・足りないときの調整は、職員の判断に任せる（1日あたりの目安額などは出さない）

3.1 商品の照合

  1. 正規化：保存時と検索時に同じ関数を使う（NFKC → カタカナをひらがなに → 「CO・OP」「コープ」の除去 → 記号・空白の除去）
  2. 完全一致：正規化名と内容量（表記をそろえたもの）が一致すれば（メーカーは両方に値があるときだけ比べる。チラシではメーカーが空のことが多いため）「前回と同じ商品」の候補にする。正規化名が同じで内容量が違えば「内容量違い」の候補にする。ここで決まったものは Claude を呼ばない
  3. 候補検索：2 で決まらない商品は、文字バイグラムの Dice 係数で上位5件を出す（しきい値 0.3。実際のチラシで精度を測り、必要なら設定で変える）
  4. Claude の判定：候補が出た商品（似ているが一致しない、迷うもの）だけを、1商品につき1回（候補5件をまとめて）Haiku に渡し、候補ごとに「同じ商品 / 味違い / 内容量違い / 別商品」を判定させ、理由を添える。1回の取り込みでの呼び出しの数には上限を設ける（設定で変える）。上限を超えた分・失敗した分は、判定なしで候補だけを示す（D-63）
  5. 職員が確定：迷う場合は「別商品」として扱う（確認する側に倒す）
  • 形態素解析・ベクトル検索は使わない（数百件の規模なので、全件の計算で足りる）

受け入れ条件

  • 抽出に失敗した場合でも、手入力で商品を追加できる（抽出結果の一覧からも、抽出結果がないときからも始められる）。取り込みの画面で手入力した商品は、職員がチラシを見て入れたものとして、チラシから読み取った商品と同じ扱い（「参考」）にし、同じ照合（3.1）と同じ選択肢（FR-FLYER-06）にかける（D-73）
  • 読み取りの検証（FR-FLYER-03g）が失敗した場合でも、抽出結果は表示する。そのとき「読み取りの検証ができなかった」ことを示す
  • 税込と税抜の整合チェック・二重の読み取りのチェックには xUnit のテストがある
  • 照合結果が「味違い」の商品は、元の商品のアレルゲン確認を引き継がない（SR-05）
  • チラシのアレルゲン表記（説明文の末尾の「（乳・小麦）」など）から得た情報は、ステータス「参考」として、書かれている品目を「含む」として記録する。推奨20品目・経過措置中のカシューナッツなども、表記に書かれていれば「含む」とする。説明文で避ける品目の「探す言葉」が当たった品目も「含む」に入れる（03 の 3の「チラシの品目」）。書かれていない品目を「含まない」とはしない。チラシの表記は表示義務のある特定原材料（9品目）が対象とみなすため、推奨20品目・経過措置中のカシューナッツ・施設の追加品目は、表記に書かれていないことからは判断しない
  • チラシを取り込んだときに「参考」の記録を追加するかは、03 の 3 の表で決める（記録がない → 追加する / 過去に「確認済み」がある → 追加しない（食い違いは SR-20）/ 「参考」だけ → チラシの品目が増えたときだけ追加する）
  • チラシにアレルゲン表記がない商品も、ステータス「参考」（情報源：チラシ、「表記なし」）として記録する。「含む」品目は空で、どの品目も「含まない」とはしない。「不明」にすると、避ける品目が設定されている施設では使い始めの週に候補がなくなるため（SR-09）。献立に使う場合は「参考」と同じく警告を出す
  • 正規化・Dice 係数の計算には xUnit のテストがある

チラシの特徴（実物のチラシで確認したこと）

  • 1枚に約20商品。お菓子だけでなく飲み物（お茶・水・ジュース・牛乳）も載っている
  • 商品ごとに4桁の注文番号がある
  • 価格は「税抜（税込）」の2つが載っている
  • 説明文の末尾に「（乳・小麦）」のようなアレルゲン表記がある（表示義務のある特定原材料が対象とみなす。調べた時点のチラシは改正前の8品目の可能性がある）
  • 「次回予定▶10月2日」のような次回の掲載予定、「値上げ」「箱でお届け」「冷蔵」などの表示がある
  • 「○カ月頃から」「1歳頃から」のような対象年齢の表示がある（乳幼児向けの商品も混ざる）
  • キャラクター名が商品名に入っている商品がある。パッケージの絵だけで分かるものもある
  • 説明文は小さい文字で、スマホで撮影すると読み取りにくい可能性がある
  • 実際に、高解像度の画像でも「(乳)」の表記を読み落とした（2026-11-02、要件づくりの中で Claude が乳性飲料・牛乳の「(乳)」を見落とした）。チラシからの読み取りは誤りがある前提で扱う

  • 入数・1人あたりの個数・税込価格は、1以上の整数だけを受け付ける
  • Claude の抽出結果を職員が確定しない限り、「確認済み」にならない（SR-03）
  • 確定画面では、原材料表示の読み取りテキストと、Claude が判定したアレルゲンを並べて表示する
  • 読み取りテキストのうち、施設の追加品目の「探す言葉」に当たった部分を強調表示する（例：「ヘーゼルナッツペースト」）
  • 原材料の全文がない（読み取れなかった）場合は「確認済み」にできない（SR-12）
  • サーバーは、Claude の読み取りが終わったらすぐにパッケージ画像を破棄する。確定の画面で見比べる画像は、ブラウザが持っているものを使う

5. 献立作成（FR-MENU）

優先度：必須

5.1 週の要望（自然言語の条件）

固定条件以外の条件は、献立を作るときに職員が文章で伝える。

例：

  • 「おやつとして、しょっぱいもの、ゼリー系を合わせて出したい」
  • 「金曜日は誕生日会があるので、豪華なおやつにしたい」
  • 「水曜日は都民の日なので、子どもが○○人」
  • 「木曜は手作りの日」「〇〇は不人気なので使わない」
  • 「（キャラクター名）のお菓子を入れたい」
ID要件
FR-MENU-01献立を作るとき、その週の要望を自由な文章で入力できる（空欄でもよい）
FR-MENU-02Claude は要望を読み取り、構造化できるものと方針として扱うものに分ける
FR-MENU-02a要望の読み取りと献立案の作成は、1回の Claude の呼び出しで行う（D-66）。要望が空欄なら、読み取りを省いて献立案だけを作る。読み取った結果は次の形で受け取る（interpreted_requests）：日ごとの値（日付・人数・日の種類・見出し。変えるものだけ）、方針の一覧（文章と、関係する日）、反映しなかった要望の一覧（文章と理由）（D-45）
FR-MENU-03構造化できるもの（日ごとの人数の変更、「手作りの日」「おやつなし」などの日の種類、「誕生日会」などの日の見出し）は、アプリの値として反映し、画面に表示する。アレルギー・予算・重複の期間を緩める要望などは反映せず、「反映しなかった要望」として理由とともに警告で示す
FR-MENU-04献立案と一緒に「要望をこう理解しました」という一覧を表示し、職員が誤りを直せる（人数・日の種類・日の見出しは画面上で直接修正できる）。「要望を直す」で手順3に戻り、要望を書き直して献立案を作り直せる（作り直す前に、今の案が消えることを確認する）。作り直しても、職員が画面で直した人数・日の種類・見出しはそのまま残す（D-57）
FR-MENU-05方針として扱うもの（組み合わせ・豪華にしたい日・避けたい商品など）は、日ごとの理由の中で「どう反映したか」を説明する

FR-MENU-06a要望にキャラクター名や味・種類が含まれる場合、商品のタグ（FR-FLYER-03a）が一致する商品を優先して選ぶ。一致する商品がチラシにない場合は、そのことを説明する

要望で変えられないもの

  • アレルギーの条件は、要望の文章では緩められない。 例えば「卵の子は今日お休み」と書かれても、アプリ側の判定はそのままにし、警告を出す。出欠は献立に反映しない（常に施設の避ける品目すべてを条件にする。Q-13）
  • 週の予算額は要望では変えられない（変えるのは職員が画面で行う）。特定の日に予算を多く使うことはできるが、週の予算を超えれば警告する
  • 人数の変更は、要望から読み取った値を画面に表示し、職員の目に触れる形で反映する（金額計算に直結するため）

5.2.1 ツールを使う献立づくり（エージェント）

FR-MENU-16 の作り方。献立案の作成とチャットでの組み直しは、はじめからこの形で作る（D-82。1回の呼び出しの版は作らない）。FR-MENU-15 の検証は submit_menu と最後の検証で必ず行い、エラーのある案は受け付けずに Claude に返す（差し戻しの回数は、ループの上限10回の中で数える）。週の要望の読み取り（D-66）も同じループの中で行い、submit_menu で読み取り結果と献立案を一緒に出させる。エージェントにするのは献立づくり（献立案の作成・チャットでの組み直し・届いた後の代わりの提案）だけとし、チラシの読み取り・照合の判定・アレルゲン抽出などは1回の呼び出しのままにする。

ツール中身（Biz が計算する）
search_products条件（分類・タグなど）でその週の掲載品を探す。判定が「入れられない」の商品（含む・含む可能性あり・不明）・価格か入数が未入力の商品・「今週は使わない」の商品は、最初から結果に入れない

check_duplicates重複ルール（FR-COND-05）の期間内の商品を返す
validate_menu案全体を FR-MENU-15 と同じ検証にかけ、問題の一覧を返す
submit_menu案を提出する。FR-MENU-15 の検証に通らなければ受け付けず、問題をエラーとして Claude に返す
  • Claude はアレルゲンを判定しない。ツールが返す結果だけを使う（SR-18）
  • 献立は submit_menu を通らないと確定しない。Claude がツールを使わずに案を返しても、最後の検証は必ず通る。submit_menu が受け付けた時点でループを止める
  • ループの回数の上限はコードで決める（10回）。上限に達したら、最後に検証を通った案、なければ問題の一覧を警告として表示する
  • ループは手書きにする（SDK のベータ機能 BetaToolRunner は使わない）。ベータ機能に頼らず、submit_menu で止める処理と回数の上限をコードで持つため
  • ツールの呼び出しは強制しない（tool_choice は auto）。どのツールを使うかはプロンプトで指示し、ツールには strict: true をつけて、引数をスキーマどおりにする
  • ツールの判断ロジックは Biz、ツールの定義（名前・説明文・JSON スキーマ）・ループ・Biz への振り分けは OyatsuBiyori.Claude に置く（NFR-MNT-05）

受け入れ条件

  • 人数・金額・週の予算・アレルゲンの判定は、Claude の出力を信用せず、アプリ側のロジック（Biz）で計算する。Claude は案・理由・要望の読み取りを担う
  • 要望から読み取った人数の変更は、画面に表示され、職員が修正できる
  • 金額計算・週の予算の計算・アレルゲン判定には xUnit のテストがある
  • Claude が存在しない商品や、チラシに載っていない商品、候補から外した商品を返した場合は、その商品を採用せずエラーとして扱う
  • 献立案の作成中は進捗を表示し、失敗したら再試行できる。作成中に画面を閉じても、サーバーで続ける（NFR-PERF-05）

金額計算の定義

必要パック数の既定 = 切り上げ（その日の人数 × 1人あたりの個数 ÷ 入数）
商品の金額         = 必要パック数（保存した値） × 税込価格
その日の金額       = その日の商品の金額の合計
1人あたり金額      = その日の金額 ÷ その日の人数
  • 必要パック数は保存する値とする。既定は上の式で求め、入れ替え案と職員の操作で上書きできる。その日の人数か1人あたりの個数を変えたら、式で求め直す。「その日の人数 × 1人あたりの個数」に足りないパック数なら警告する（FR-MENU-08a）
  • 「1人あたりの個数」は商品ごとに既定値を持ち（default_per_child_count、既定1）、献立に入れるときに写す。献立の中で個別に変えられる
  • 入数・1人あたりの個数は1以上の整数、税込価格は1以上の整数とする（0で割らないため）。日ごとの人数は0以上の整数とする
  • 税込価格と入数は、注文できる単位1つあたりとする（「箱で」のまとめ買いは、1箱の価格と1箱の入数）
  • 端数の扱い（1人あたり金額の円未満）は表示時に四捨五入する（計算は小数のまま）
  • 日の種類が「手作り」「おやつなし」の日、人数が0の日は、その日の金額を0とし、1人あたり金額は「—」と表示する（0で割らない）。「手作り」の日の材料費は扱わない
  • 「手作り」「おやつなし」の日に商品が残っていても、金額は0のままとし、「金額に含まれていません」と警告する（D-77）

03. アレルゲンの扱い（安全要件）

子どもの安全に直結するため、この文書の要件は他のすべての要件に優先する。
迷ったら「確認する側」に倒す。

1. 基本方針

  • AI（Claude）の判定は候補であり、確定は必ず職員が行う
  • アレルゲン情報が確かでない商品を、「食べられる」とは扱わない
  • 「表示なし」を「含まない」とみなさない場合がある（推奨20品目と、表示義務の経過措置中のカシューナッツ）
  • 29品目に入らない食材もある（ヘーゼルナッツ・ペカンナッツなど）。29品目のチェックだけで「食べられる」と判断しない
  • 情報はいつか古くなる（リニューアルで原材料が変わる）。確認には期限を設ける

現場で起きたこと（この設計の根拠）

ナッツを避けたかったのに、ヘーゼルナッツペーストが入ったお菓子を選んでしまったことがある。

ヘーゼルナッツは29品目（2026年3月までは28品目）に入っていないため、アレルゲン表示（「一部に〜を含む」）に出てこない。原材料名には「ヘーゼルナッツペースト」と書かれているが、アレルゲン表示だけを見ると見落とす。
また「ナッツ」は1つの品目ではない。29品目では、くるみ・カシューナッツが特定原材料、アーモンド・マカダミアナッツ・ピスタチオが推奨品目で、それ以外のナッツは対象外になっている。

2. 対象のアレルゲン

品目は制度改正で変わることがあるため、コードに直書きせずマスタデータとして持つ。実装時に消費者庁の最新情報を確認する。

2026年4月1日の食品表示基準の改正で、28品目から 29品目 に変わった（カシューナッツを特定原材料に変更、ピスタチオを特定原材料に準ずるものに追加）。カシューナッツの表示義務には経過措置があり、2028年4月1日に完全義務化される。それまでは、カシューナッツを含んでいても表示されていない商品がありうる（2026-11-03 確認）。

2.4 コープのカートの絞り込みとの関係

コープの注文サイトには、カートに入れるとアレルギーのある商品を除外する機能がある（Q-15）。

  • そのため、コープの絞り込みを通ったことを「確認済み」の根拠にしない。使う場合も、情報源「コープのサイト」として「参考」扱いにする
  • このアプリは注文と連携しない。献立を決めたあとの発注時に、コープの絞り込みをもう一段の確認として使うのは構わない（職員への案内として書く）

  • チラシから取り込んだ商品は、アレルゲン表記がなくても「参考（表記なし）」として記録する。「含む」品目は空で、どの品目も「含まない」とはしない（FR-FLYER の受け入れ条件）。チラシを通さずに商品を登録する機能はない（FR-PROD-10 は欠番）ため、ふだん「不明」は起きない。データの不整合などに備えて、判定には残す

  • チラシから得る品目は、アレルゲン表記に書かれた品目と、説明文に避ける品目の「探す言葉」が当たった品目を合わせたもの（以下「チラシの品目」）。説明文そのものは保存せず、当たった言葉を source_note に残す

5. 判定ロジック（Biz に置き、xUnit でテストする）

判定の結果は、献立での扱いによって3つに分ける。ステータスより先に「含む」を調べる（「参考」でチラシに「（卵）」とある商品を、警告だけで使えるようにしないため）。

区分判定献立での扱い
入れられない（エラー）含む / 含む可能性あり / 不明（避ける品目が1つでもあるとき）Claude に渡す候補・入れ替え案から除く。手動で入れると理由を表示し、確定できない（職員の確認の操作でも確定できない）
警告（確認すれば使える）参考 / 要再確認 / 未確認の品目あり / 不明（避ける品目がないとき）候補にしてよい。確定時に商品ごとの確認が要る（SR-04・SR-22）
安全上のどれでもないそのまま使える。「メーカーへの確認が必要」を添えることがある（SR-06）
商品の判定(商品, 避ける品目, 今日):
    最新     = 商品の最新の確認記録（なければ「なし」）
    確認済み = 最新の「確認済み」の記録（なければ「なし」）
    有効     = 確認済み と、それより後のすべての記録（確認済みがなければ、すべての記録）
    含む品目 = 有効 の「含む」品目の和集合
    全文     = 有効 の原材料の全文（読み取り・職員の修正の両方）
    もし 避ける品目 ∩ 含む品目 ≠ 空                             → 含む（エラー）
    もし 正規化した商品名 か 全文 に、避ける品目の「探す言葉」がある → 含む可能性あり（エラー）
    もし 最新がない:
        もし 避ける品目が1つでもある                           → 不明（エラー）
        それ以外                                                → 不明（警告）
    もし 最新.ステータス = 参考                                 → 参考（警告）
    もし 今日 - 確認済み.確認日 > 再確認期間                     → 要再確認（警告）
    もし 避ける品目のうち、確認済み で確定していない品目がある     → 未確認の品目あり（警告）
    もし 避ける品目に「表示が確実でない」品目がある               → 安全（「メーカーへの確認が必要」を添える）
    それ以外                                                    → 安全

  • 判定は保存せず、表示・検証のたびにこの関数で求める（避ける品目・探す言葉・再確認期間が変わっても、すぐに反映されるようにする）
  • 「探す言葉」・商品名・原材料の全文は、同じ正規化（NFKC → カタカナをひらがなに → 空白・改行・記号を除く）をしてから部分一致で探す。パッケージの全文は語の途中で改行されることが多いため、改行も除く。「CO・OP」「コープ」の除去は商品の照合だけで使い、ここでは使わない

テストで必ず確かめること

  • 記録がない商品は安全と判定されない
  • 「参考」「不明」の商品は、含む品目が空でも安全と判定されない
  • 「参考」で避ける品目を「含む」商品は、警告ではなくエラー（入れられない）になる
  • 避ける品目が1つでもあるとき、「不明」はエラーになる。ないときは警告になる
  • 商品名に「探す言葉」がある「参考」の商品（例：「ヘーゼルナッツクッキー」）は、全文がなくてもエラーになる
  • 職員が直した全文から言葉を消しても、Claude が読み取った全文に言葉があればエラーになる
  • 再確認期間の境界（ちょうど90日・91日）の判定
  • 最新の記録が「参考」で、それより前に「確認済み」がある場合は、最新（参考）が優先される
  • 避ける品目に「表示が確実でない」品目（推奨20品目・経過措置中のカシューナッツ）があるときに、注意表示が出る
  • ヘーゼルナッツの事例：ヘーゼルナッツを避けているとき、アレルゲン表示が「小麦・乳・大豆」で、原材料に「ヘーゼルナッツペースト」を含む商品は安全と判定されない
  • 職員が「ヘーゼルナッツ：含まない」と確定していても、原材料の全文に「ヘーゼルナッツ」があればエラー（含む可能性あり）になる
  • 「探す言葉」の検索は、正規化（NFKC・カタカナ／ひらがな・空白と改行と記号の除去）したうえで行い、全角・半角の違いや、「ヘーゼル（改行）ナッツペースト」のような改行で見落とさない
  • 「参考」の記録で「乳・卵」→ 次のチラシで「乳」だけになっても、卵は「含む」のまま（エラーのまま）
  • 「確認済み」の記録のあとに、含む品目のない「参考」の記録を足しても、確認済みの「含む」は残る
  • 新しい「確認済み」の記録で「含まない」にした品目は、それより前の「参考」の「含む」に引きずられない
  • 避ける品目に新しい品目を追加したとき、その品目を確定していない商品は安全と判定されない
  • 「確認済み」の商品にチラシを取り込んでも、「参考」の記録は追加されない（SR-20 の食い違いがある場合を除く）
  • チラシの表記に、確認済みでは「含まない」の避ける品目があるとき、エラーになる（SR-20）
  • 確定時に確認した警告は、判定が変わると確認していない状態に戻る（SR-22）

6.3 そのほかの表示

  • 「メーカーへの確認が必要」（SR-06）は、アレルゲン確認の画面・商品詳細・今週の商品の一覧に小さく添え、献立の日ごとのカードには出さない（ナッツ類を避けていると多くの商品に出るため、ほかの警告が読まれなくなるのを防ぐ）。そのかわり、献立の確定のダイアログの末尾に1行で必ず出す（例：「ナッツ類の一部は表示されないことがあります。気になる商品はメーカーに確認してください」）
  • 避ける品目が1つも設定されていないときは、今週の商品（SC-09 手順2）・商品一覧（SC-06）・献立案（SC-09 手順4）の上部に「避ける品目が設定されていません」と表示し、設定（SC-04）へ進めるようにする（判定は変えない。このときは「含む」「含む可能性あり」「不明（エラー）」が起きないため、すべて 🟢 か 🟡 になる）
  • 確定のときの商品ごとのチェックは、警告の理由と次にすることを確かめたことを示す1文にする（例：「☐ フルーツゼリー：チラシの情報だけです。届いたらパッケージで確認します」）。「確認しました」だけの文言にしない（届く前の商品はパッケージを見られないため。SR-04）
  • 確定のときに「届いたら確認する」とした商品が、届いたあとも確認されないまま残らないように、献立一覧（SC-10）の上部で「今日以降の献立で使う、パッケージで確認する商品」を最初に示す
  • 「確認し直し」（D-71・D-85）のバッジは黄（警告と同じ色）にする
  • 警告の文言は、何をすればよいかを含める（例：「パッケージの原材料表示を撮影して確認してください」）
  • 「アレルゲンの最終確認は、必ずパッケージの原材料表示で行ってください」の注意書きを、ログイン後の画面に常に出すことはしない（D-89）。何をすればよいかは、🟡・🔴 の理由と次にすることで商品ごとに示す
  • アレルゲン確認の画面では、原材料表示の全文の中で「探す言葉」に当たった部分を強調表示する（例：「ヘーゼルナッツペースト」に色をつける）

04. データ要件

論理的なデータ構造を示す。物理設計（型・インデックス・マイグレーション）は実装時に決める。

1. 方針

  • 主キーはアプリ側で振る UUID（文字列）
  • すべてのエンティティに更新日時・更新者を持たせる（EntityBase）。更新者は NULL 可（マスタのシードと、システムの処理で更新するため）。シードの主キーと日時は固定の値にする（07 の D-80）
  • JAN コードは NULL 可・UNIQUE（チラシには JAN がないため）
  • アレルゲン確認は上書きせず、履歴として積み上げる
  • チラシ・パッケージの画像は保存しない。抽出した事実だけを残す
  • チラシ自体は保存しない。価格・注文番号などは取り込むたびに商品に上書きする。献立の候補は、その献立に保存した掲載品の写し（menus.listed_products）で決める（FR-FLYER-07）
  • 価格は号ごとに変わるため、献立の商品には献立に入れた時点の価格・注文番号を保存する（過去の献立の金額が変わらないようにする）
  • 日時は UTC で保存する。SQLite は日時が UTC かどうかを保存しないため、読み出した日時はすべて UTC として扱う（画面で9時間ずれないようにする。D-80）。「今日」「週（月曜始まり）」「月」の判定は日本時間（Windows のタイムゾーン ID は Tokyo Standard Time）の日付で行う。日付だけの項目（week_start・date）は日本時間の日付をそのまま持つ
  • アレルゲンの判定（入れられない / 警告 / 安全）と、届いた後の警告（FR-MENU-36）は保存せず、表示・検証のたびに求める（07 の D-15）

SC-13 ランディング

ルート（/）に表示する。ログインしなくても見られる。実データを出さない（FR-LP-01）。上から次の順に並べる。

  1. ファーストビュー：アプリ名・一言の説明・「ログイン」ボタン・献立案の画面の画像。ボタンはログインしていてもいなくても「ログイン」とし、ランディングではログインの状態を確かめない（API を呼ばない）。ログイン済みなら、ログイン画面（SC-01）から献立一覧へ移る（07 の D-69）
  2. こんな悩みはありませんか：毎週1〜2時間・条件が多い・気が抜けない（FR-LP-03）
  3. 使い方：撮る → 確かめる → 伝える → 直す の4ステップを、画面の画像つきで（FR-LP-04）
  4. できること：理由つきの提案・文章で伝える要望・予算に合わせる入れ替え案・重複の警告（FR-LP-05）
  5. 安全への考え方：アプリが必ずチェックすること / 職員が確定すること / 3つの表示（🔴 使えません・🟡 要確認・🟢 使えます） / 29品目外の食材（FR-LP-06）。色を変えた区画にして、ほかの区画より目立たせる
  6. デモ動画（あると良い。FR-LP-08）
  7. 作った理由：開発の背景（FR-LP-09）
  8. フッター：ハッカソン名・GitHub・Claude の表記（FR-LP-10）
  • 画面の画像は、ダミーデータを入れた環境で撮る（FR-LP-07）
  • やわらかい雰囲気にする（「おやつ日和」の名前に合わせ、明るい色・丸みのある形）。ただし安全の区画は落ち着いた色で、きちんと読ませる

SC-01 ログイン

  • ログイン名とパスワードを入れてログインする。成功したら献立一覧（SC-10）へ移る
  • ログイン済みの状態でこの画面を開いたら、すぐに献立一覧へ移る（D-69）
  • 初期パスワードのままなら、パスワード変更（SC-12）へ移る（FR-AUTH-03b）

SC-02 ホーム（左サイドバーの枠）

  • ログイン後のすべての画面の枠。左のサイドバーで「献立一覧」「商品一覧」「設定」を選ぶ。ログアウトもここに置く
  • ホーム専用の中身は持たない。ログイン直後は献立一覧（SC-10）を表示する
  • PC ではサイドバーを常に表示し、上部のボタンで開閉できる。閉じるとアイコンだけの細い帯になり、そこからも各画面へ移れる。開閉の状態はブラウザに保存する。スマホでは折りたたみ、≡ ボタンで開く

SC-10 献立一覧

  • 上部に、必要なときだけ注意を出す（何もなければ出さない）。「パッケージで確認する商品」は、🟡 要確認の商品と、情報がないため 🔴 使えませんになっている商品のこと（03 の 6.3）
    • 「今日以降の献立で使う、パッケージで確認する商品が n件あります」（下書き・確定の献立に入っている商品。「使わない」にした商品も数える）。確定のときに「届いたら確認する」とした商品を、届いたあとに見落とさないため。「商品を確認する」で商品一覧（SC-06）をその絞り込みで開く
    • そのほかの、パッケージで確認する商品（献立で使っていない商品）と未確定の献立の件数は出さない。前者は商品一覧の絞り込み、後者は週ごとの一覧の状態で分かる
  • 届いた商品の確認で 🔴 使えませんになった商品を使う献立があれば、ほかの表示より目立つ形で最上部に出す（例：「11/12（水）の献立に、避ける品目（卵）を含む商品があります」）。そこから献立を開ける（FR-MENU-36）
  • 週ごとの一覧：対象週・状態（未作成 / 下書き / 確定）・「週の実績 / 週の予算」（超えたら、超えた額）・警告のバッジ（「🔴 使えません 1件」「🟡 要確認 3件」「確認し直し 2件」。FR-MENU-34a）・週のメモ（あると良い）。今週・来週・再来週は、未作成でも行を出す
    • 献立一覧には「今週とこれから」（今週以降の週）だけを出す。今週を一番上にして枠で目立たせ、古い順（来週・再来週…）に並べる。最後に「さらに先の週の献立を作る」を置く
    • 今週より前の週は「過去の献立」（SC-14）で見る。一覧の下に「過去の献立を見る（n週）」を置く（過去の週がなければ出さない）
  • 下書きは、行のメニューから削除できる（確認のダイアログあり。FR-MENU-31a）
  • 未作成の週は「献立を作る」、下書き・確定の週は「開く」で SC-09 へ進む
  • 「週を選んで献立を作る」（日付を選んで、一覧に出ていない週の献立を作る入口）は置かない（D-88 で取りやめ。D-49）。今週より先の週は「さらに先の週の献立を作る」で作る
  • PC では、上部の注意・見出し・「さらに先の週の献立を作る」・「過去の献立を見る」を固定し、週のカードの部分だけをスクロールする
  • 「確認し直し」のバッジは、献立のカードで警告の商品にチェックを付け直すと消える。献立は確定のまま（D-71）
  • 印刷（FR-LIST-04）・商品名での検索（FR-LIST-02）はあると良い

SC-14 過去の献立

  • 献立一覧（SC-10）の「過去の献立を見る」から開く（/menus/history）。サイドバーの項目は増やさない（「献立一覧」を選んだ状態のまま）。「献立一覧へ戻る」で戻る
  • 今週より前の週を新しい順に出す。項目は SC-10 の週ごとの一覧と同じ（対象週・状態・「週の実績 / 週の予算」と差額・警告のバッジ）
  • PC は表（MUI X の DataGrid）で、画面の高さいっぱいに出し、表の中だけをスクロールする。🔴 の商品がある週は行に色を付ける（バッジの文言もある）。スマホはカードで出す
  • 「開く」で SC-09 へ進む。下書きは行のメニューから削除できる（FR-MENU-31a）
  • 過去の献立の中身の表示（FR-LIST-01）・商品名での検索（FR-LIST-02）・印刷（FR-LIST-04）は、この画面に足す（あると良い）

SC-09 献立作成

献立一覧（SC-10）の「献立を作る」「開く」から入る。チラシの取り込みから献立の確定までを、1つの画面で4つの手順に分けて進める（画面上部に手順を表示し、終わった手順には戻れる）。
SC-05（チラシ取り込み）は、この画面の手順1にまとめたため欠番とする。

  • 途中でやめても、それまでの内容（確定した商品・今週は使わない指定・要望・献立案）は下書きとして保存され、再開できる。撮影はスマホ、献立案は PC のように、途中で端末を変えて続けられる。確定前の読み取り結果は、サーバーのメモリに24時間だけ残る（再起動したら読み取り直し。FR-FLYER-10）

手順1：チラシ取り込み

その週のチラシを取り込み済みなら飛ばして手順2から始める。手順2から「チラシを取り込み直す」で戻れる。

  1. チラシを取り込む（複数枚可）。対象週は献立で選んだ週を使う
    • 「カメラで撮る」「ファイルを選ぶ」の2つのボタンを並べる。PC では画面にファイルをドラッグ＆ドロップしても追加できる
    • 撮影の前に「小さい文字が読めるよう、1ページを半分ずつ近づけて撮ってください」と案内する
    • PDF はページをサムネイルで並べ、取り込むページを選ぶ（FR-FLYER-01a）
    • 取り込んだ画像・PDF のページをサムネイルで並べ、不要なものを外してから「読み取る」を押す（10枚まで）
  2. 抽出中の進捗を表示する。画面を閉じても読み取りは続き、戻ると結果が出る（FR-FLYER-10）
  3. 抽出結果の一覧：商品ごとに次を表示し、職員が確定する
    • 照合結果（同じ商品 / 味違い / 内容量違い / 新規）と理由。確定の選択肢は「同じ商品」「味違い・内容量違いとして登録」「新しい商品として登録」「取り込まない」（FR-FLYER-06）
    • 読み取った商品名・内容量・税込価格・注文番号・入数の候補と理由・おやつの分類・タグ。どれも直せる
    • 読み取ったアレルゲン表記（「乳・小麦」）、または「表記なし」と読まれたこと（FR-FLYER-04a）
    • 読み取りの検証で疑わしい項目の印と理由（FR-FLYER-03h）。検証ができなかった場合はその旨
    • 「確認済み」の商品で、チラシの表記と食い違う場合はその内容と選択肢（FR-FLYER-09・SR-20）
    • 確定した商品は「確定済み」の印を付けて一覧に残し、選び直せる（D-53）
    • 一覧は表（MUI X の DataGrid。列：開閉・状態・商品名・アレルゲン表記・同じ商品か。スマホでもアレルゲン表記が横にスクロールせずに見えるよう、商品名のすぐ右に置く）。状態は「警告あり（食い違い・説明文の避ける品目の言葉・品目に当てはめられない語・検証の指摘）/ 要確認（同じ商品かどうかが決まっていない・表記なし）/ 未確定 / 確定済み」で、この順に並べる（確定済みは必ず下。列での並べ替えはしない）。表の上のタブで状態ごとに絞り込める
    • 状態のチップの下に、何を確かめるのかを短く添える（「表記なし」「同じ商品か選ぶ」など。アレルゲンに関わるものを先に並べ、確定済みの行にも出す）。アレルゲン表記の列には、読み取った表記の原文と、品目・表記なし・説明文の避ける品目の言葉・パッケージでの確認との食い違い（避ける品目なら error の色）のチップを出す
    • 表の上の「未確定を1件ずつ確かめる」で、未確定の商品を1件ずつダイアログで確かめられる（前へ・あとで・確定。決めるのはボタンを押したときだけ）
    • 確定のフォームは、直してほしい欄（指摘がある・読み取れず空）だけを出し、ほかの欄は1行の要約にまとめて「ほかの項目も直す」で開く。アレルゲン表記と、品目の分からない語の欄はいつも出す
    • 確定の操作は、行の下に開く詳細欄で行う。詳細欄の先頭に「確かめること」（理由ごとに、どこを見て何を選ぶ・直すか）を出し、検証の指摘は当てはまる入力欄のそばに出す。初めはどの行も閉じておき、確定したら次の未確定の行を開く。スマホでは表を横にスクロールでき、詳細欄は画面の幅に収める
  4. 一覧の上部に「『同じ商品』をまとめて確定」ボタンと、確定していない件数（「確定していない12件は今週の商品に入りません」）を出す
  5. 読み落としの指摘と、手入力で商品を追加する入口を一覧の下に置く

手順2：今週の商品

今週のチラシに載った商品を一覧で表示する。Claude に献立を作らせる前に、候補とアレルゲンの表示を職員が見渡せるようにする。

  • 商品ごとに、商品名・価格・おやつの分類・タグ・アレルゲンの表示（🔴 使えません / 🟡 要確認 / 🟢 使えます）と理由を表示する（03 の 6。例：「🔴 使えません：卵を含みます」「🟡 要確認：チラシにアレルゲンの表記がありません」）
  • 避ける品目が1つも設定されていなければ、一覧の上部に「避ける品目が設定されていません」と表示し、設定（SC-04）へ進めるようにする（03 の 6.3）
  • 重複ルールの期間内の商品は「○日前に出した」と表示する
  • 避ける品目に「表示が確実でない」品目があるときは、「メーカーへの確認が必要」を小さく添える（SR-06）
  • 税込価格か入数が未入力の商品は「入数を入れてください」と表示し、その場で入力できる（FR-MENU-07c）
  • 🟡・🔴 の商品から、その場でアレルゲン確認（SC-08）へ進める
  • 商品ごとに「今週は使わない」を指定できる
  • アレルゲンの表示（すべて / 🟡 要確認 / 🔴 使えません）とおやつの分類で絞り込める
  • 一覧の上部に件数のまとめを表示する（例：「献立に入れられる商品 15件（うち 🟡 要確認 4件）／ 🔴 使えません 2件」。🟢 の「使えます」と混ざらないよう、「使える」とは書かない）

手順3：要望の入力

  1. その週の要望を文章で入力し、「献立を作る」を押す（空欄でもよい）。入力欄には例文を薄く表示する
    • 例：「しょっぱいものとゼリー系を合わせて出したい」「金曜は誕生日会なので豪華に」「水曜は都民の日なので子どもが○○人」
    • 入力欄の近くに「子どもの名前は書かないでください」と、「要望の文章では、避ける品目（アレルギー）の条件は変えられません」を表示する
    • 横に「いつもの条件」（人数・週の予算・避ける品目・重複ルール）を読むだけで表示し、「変更」で設定へ移れる。1日あたりの目安額は出さない（Q-14）
    • （あると良い）よく使う要望を、押すと入力欄に入るボタンとして並べる
  2. 「自分で組む（AI を使わない）」を選ぶと、日ごとの枠だけの献立を作り、手順4で手動で商品を入れる（FR-MENU-07d）

手順4：献立案とチャット

  • 上部に「要望をこう理解しました」の一覧（例：「水曜：人数 ○○人」「金曜：豪華にする」「毎日：しょっぱいもの＋ゼリー系」）。人数・日の種類・日の見出しはその場で修正できる。「要望を直す」で手順3に戻れる（FR-MENU-04）
  • PC では左に献立（日ごと）、右にチャットを並べる。スマホではタブで切り替える
  • 献立案の作成中は、進捗を段階で示す（例：「要望を読み取って、献立を考えています」→「条件を確かめて、直しています」。要望の読み取りと献立の提案は1回の呼び出し（D-66））。
  • 日ごとのカード：日の見出し（「誕生日会」など）・商品・1人あたりの個数・パック数・金額・1人あたり金額（円未満は四捨五入）・理由・警告
  • カードで、商品の入れ替え・追加・削除、1人あたりの個数とパック数の変更、日の種類（通常 / 手作り / おやつなし）の切り替えができる（FR-MENU-24）。パック数は人数と個数から求めた値が入り、職員が上書きできる。人数か1人あたりの個数を変えると、求め直す（D-43）
  • 避ける品目が1つも設定されていなければ、上部に「避ける品目が設定されていません」と表示する（03 の 6.3）
  • 警告は種類ごとに分けて示す：🔴 使えません の商品（赤）・🟡 要確認 の商品（黄）。どちらも理由を添える（03 の 6.2）・「○日前に出した」（重複）・直しきれなかった検証の問題・パック数が全員分に足りない（D-43）・通常の日に商品がない・「手作り」「おやつなし」の日に商品がある（D-75）。「手作り」「おやつなし」の日の商品は金額を0のままにし、「金額に含まれていません」と示す（D-77）
  • 週の予算を超えたら、予算の表示の横に警告を出す
  • 作成に失敗したときは、理由と「もう一度作る」ボタンを出す（入力した要望は残す）
  • 届いた後の確認で 🔴 使えませんになった商品がある日は、カードに警告を出す（例：「🔴 使えません：卵を含みます。別の商品に替えてください」）。代わりの提案（あると良い。FR-MENU-38）があれば、カードから選べる
  • 「週の実績 / 週の予算」を常に表示し、週の予算はその場で上書きできる（例：金曜は店で買うケーキなので、その分を下げる）
  • 「週の実績」が週の予算に届かないときだけ「予算に合わせる」ボタンを出す（予算ちょうど・超えているときは出さない。07 の D-67）。押すと入れ替え案（例：「水曜の〇〇を△△に → 週の予算ちょうど」「火曜に□□を追加」）を最大3件、Claude の説明つきで表示する。選ぶと反映する（FR-MENU-28・30）
  • 商品ごとにおやつの分類（しょっぱい / あまい / のどごし）を表示する
  • 商品のタグ（キャラクター・味）を小さく表示し、要望との対応が分かるようにする
  • 警告のある商品から、その場でアレルゲン確認（SC-08）へ進める
  • 「下書き保存」「確定」ボタン。確定時は確認のダイアログを出す（FR-MENU-32）
    • エラー（🔴 使えません の商品・価格か入数が未入力の商品・その週の掲載品にない商品）があれば、その一覧を示し「確定する」は押せない（07 の D-78）
    • 🟡 要確認 の商品は1件ずつチェックを付ける。すべてに付けると「確定する」が押せる。チェックの文言は、次にすることを含めた1文にする（例：「☐ フルーツゼリー（11/12 水）：届いたらパッケージで確認します」。03 の 6.3）
    • 避ける品目に「表示が確実でない」品目があるときは、ダイアログの末尾に「メーカーへの確認が必要」の1行を必ず出す（03 の 6.3）
    • 候補から外した商品（「今週は使わない」にした商品など）は、確定では警告として示す（確定は止めない。D-78）。通常の日に商品がない日、「手作り」「おやつなし」の日に商品がある日も警告として示すだけで、確定は止めない（D-75）
  • 確定済みの献立を開いたときは、確定済みであることを示す。商品・個数・日の種類などを直し始めたら下書きに戻り、もう一度「確定」を押す（確定時と同じチェックをやり直す。07 の D-54）。警告の商品にチェックを付け直すだけなら、確定のまま（「確認し直し」。D-71）

SC-08 アレルゲン確認

  1. パッケージの原材料表示を撮影（または画像ファイルを選ぶ。4枚まで）
  2. 撮った画像と、読み取った原材料テキストを並べて表示する。テキストは職員が直せる。読み取れなかった場合や Claude が使えない場合は、テキストを手で入力できる（FR-PROD-05a）。テキストが空のあいだは、情報源がパッケージの記録ボタン（手順5）を押せない（SR-12）
  3. 29品目の判定候補（含む / 含まない）を並べて表示
    • 施設が避けている追加品目（ヘーゼルナッツなど）も判定対象に並べる
    • 原材料テキストのうち「探す言葉」に当たった部分を色で強調する（例：「ヘーゼルナッツペースト」）。職員が「含まない」にしても 🔴 使えません の表示は消えないことを、その場で示す（SR-14）
    • Claude が「含む」としなかった品目は未確定のまま並べる。「残りをすべて含まないにする」を職員が押して確定する（自動では確定しない。FR-PROD-06）

4. UI の方針

  • スマホ（縦向き）と PC の両方で使える。撮影する画面・手順（SC-08、SC-09 の手順1）はスマホ優先、献立案（SC-09 の手順4）は PC 優先で設計する
  • PC では、画面全体を縦にスクロールさせない。見出し・絞り込み・合計・「保存」「次へ」などのボタンは画面の高さの中に固定し、一覧や明細の部分だけをスクロールする（表の見出しの行も残す）。2列の画面（商品詳細・要望の入力など）は、列ごとにスクロールする。スマホでは、ページ全体をスクロールする（入れ子のスクロールは指で操作しにくいため）
  • 文言は日本語で、専門用語を避ける（例：「正規化」「照合」は画面に出さず「同じ商品かどうか」と書く）
  • Claude の処理は数十秒〜数分かかることがあるため、進捗を表示し、二重送信を防ぐ
  • Claude の出力（理由・説明・チャットの返答）は、テキストとして表示する（HTML として描画しない。NFR-SEC-11）
  • モック（mocks/）と要件定義が食い違う場合は、要件定義に従う（食い違いの一覧は 07 の 4）
  • アレルゲンは、どの画面でも「🔴 使えません / 🟡 要確認 / 🟢 使えます」の3つの表示と、理由・次にすることで示す。色と文字（絵文字かアイコン）の両方で示し、文言はフロントの共通部品だけから出す（03 の 6）
