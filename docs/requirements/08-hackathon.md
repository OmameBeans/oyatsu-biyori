# 08. 提出物と開発の進め方（ハッカソン）

ハッカソン「Built with Claude: Japan 2026」の審査基準に応えるための要件。アプリの機能ではなく、提出物・デモ・開発の進め方を定める。

| 審査の観点 | 配点 | この文書で応える節 |
| --- | --- | --- |
| インパクト | 30% | 3. 現場での試用、4. API 費用 |
| デモ | 25% | 1. 提出物、2. デモ |
| Claude の活用 | 25% | 5. Claude Code の活用（アプリ内の使い方は [02 の 9](02-functional.md#9-claude-の利用箇所まとめ)） |
| 深さと実行力 | 20% | 3. 現場での試用、6. 試行錯誤の記録 |

## 2. デモ（HK-DEMO）

優先度：**必須**

### 2.1 素材

| ID | 要件 |
| --- | --- |
| HK-DEMO-01 | **架空のダミーのチラシ**を作る（画像と PDF の両方）。実物のチラシは、権利の面で失格のおそれがあるため、**動画にも使わない** |
| HK-DEMO-02 | ダミーのチラシは、実物の特徴を再現する：1枚に約20商品・4桁の注文番号・「税抜（税込）」の価格・説明文の末尾の「（乳・小麦）」の表記・表記のない商品・飲み物・対象年齢の表示・キャラクター風の架空の商品名（実在のキャラクターは使わない） |
| HK-DEMO-03 | **ダミーのパッケージ画像**（原材料表示）を作る。少なくとも1つは、アレルゲン表示が「小麦・乳・大豆」で、原材料名に「ヘーゼルナッツペースト」を含むものにする |
| HK-DEMO-04 | **ダミーデータの投入**の仕組みを作る：商品（数十件。確認済み・参考・不明・要再確認が混ざる）・過去の確定献立（重複の警告が出るもの）・アレルゲン確認の履歴・条件設定（人数40〜70人・既定の週の予算・避ける品目に「ナッツ類（すべて）」を含む） |
| HK-DEMO-05 | ダミーのチラシ・パッケージ画像・投入データはリポジトリ直下の `samples/` に置き、リポジトリに入れてよい。ランディングページの画面の画像も、この環境で撮る（[FR-LP-07](02-functional.md#8-ランディングページfr-lp)） |

### 2.2 台本（3分）

冒頭で「誰の、どんな課題を、どう解決するか」を言い切り、山場にヘーゼルナッツの場面を置く。

| 時間 | 場面 | 見せること |
| --- | --- | --- |
| 0:00〜0:25 | 課題 | 学童の職員が毎週1〜2時間かけている。アレルギー・予算・人数・行事を同時に考え、保育の合間に気が抜けない |
| 0:25〜0:50 | チラシを撮る | スマホでダミーのチラシを撮る → 商品が読み取られ、前回と同じ商品かどうかが示される |
| 0:50〜1:20 | 要望を伝える | 「金曜は誕生日会なので豪華に」「水曜は子どもが○○人」→「こう理解しました」→ 理由つきの献立案。避ける品目を含む商品（入れられない商品）は、最初から候補に入らないことを今週の商品で示す |
| 1:20〜1:45 | チャットで直す | 「金曜をもう少し豪華に」→ 直った献立案 → 週の予算に少し届かない →「予算に合わせる」で入れ替え案（ボタンは予算に届かないときだけ出る） |
| 1:45〜2:30 | **ヘーゼルナッツ** | 現場で実際にあった見落としを紹介 → パッケージを撮る → アレルゲン表示は「小麦・乳・大豆」だけなのに、原材料の「ヘーゼルナッツペースト」が強調され「含む可能性あり」→ 献立に警告が出る |
| 2:30〜2:50 | 安全への考え方 | アプリが必ずチェックすること / AI は候補で、確定は職員 / 現場での試用の結果（かかった時間・感想） |
| 2:50〜3:00 | まとめ | 1週間あたりの API 費用・続けて使う場面 |

- Claude の処理を待つ時間は、編集で短くしてよい（短くしたことは画面に示す）
- 子どもや施設が特定できる情報は映さない

## 3. 現場での試用（HK-TRIAL）

優先度：**必須**

| ID | 要件 |
| --- | --- |
| HK-TRIAL-01 | 締切までに、現場の職員に実際に使ってもらう。**本番の環境で実際のチラシを使う**（D-76）。実データを扱うため、試用の前に本番の HTTPS・ログイン・バックアップ・費用の上限を入れておく。試用の画面や実際のチラシは、動画・README・リポジトリに載せない（動画はダミーデータの環境で撮る。HK-DEMO-01） |
| HK-TRIAL-02 | 「チラシの取り込み → 献立の確定」にかかった時間を測る。今の方法（毎週1〜2時間）と比べる |
| HK-TRIAL-03 | 感想と、迷った操作を記録する。直したことは [07 の決定の記録](07-open-questions.md#3-決定の記録) に残す |
| HK-TRIAL-04 | 結果（時間・感想の要約）を、動画・README・ランディングページに載せる。子どもや施設が特定できることは書かない |
| HK-TRIAL-05 | ハッカソン後も使い続ける場面を書く：毎週の献立づくり（PC）・届いた商品の確認（スマホ）。同じ悩みを持つ現場（保育園・放課後等デイサービスなど）にも当てはまることを示す |

## 5. Claude Code の活用（HK-CC）

優先度：**必須**

審査基準の「Claude Code を開発の中心に据え、何が可能になったか」「モデルや機能（Skills・サブエージェント・MCP・フック）を目的に応じて選び、使い分けているか」に応える。**何のために、どれを選んだか**を README に書く。

| ID | 機能 | 使い方 | 目的 |
| --- | --- | --- | --- |
| HK-CC-01 | フック | 要件定義の md を直したら HTML を作り直す / 生成物の `index.html` の直接編集を止める（作成済み） | 要件定義の md と HTML のずれを防ぐ |
| HK-CC-02 | フック | コミット前に、`docs/context/`・DB ファイル・`samples/` とフロントの素材フォルダ以外の画像や PDF・API キー（`sk-ant-`）・IP アドレスが入っていないかを確かめ、入っていれば止める（作成済み：`.claude/hooks/check-commit.py`） | 公開リポジトリへの漏えいを防ぐ（[NFR-SEC-09](06-non-functional.md)） |
| HK-CC-03 | フック | Biz のコードを編集したら、xUnit のテストを走らせ、失敗したら Claude に直させる（作成済み：`.claude/hooks/run-biz-tests.py`。テストプロジェクトができるまでは何もしない） | 安全・金額のロジックの壊れにすぐ気づく |
| HK-CC-04 | サブエージェント | 変更が安全要件（[SR-01〜22](03-allergen-safety.md)）を破っていないかをレビューする専用のエージェント。見落としが許されないため、モデルは Opus にする（作成済み：`.claude/agents/allergen-safety-reviewer.md`） | 子どもの安全に関わる部分を、別の目で必ず確かめる |
| HK-CC-05 | Skills | ダミーデータの投入、デモ環境の準備など、決まった手順を Skill にする | 手順を毎回説明しなくて済む |
| HK-CC-06 | E2E・MCP | 画面ごとに Playwright の E2E（`src/oyatsubiyori.client/e2e/`、`npm run e2e`）を書き、画面を変えたらコミット前に走らせる。満たすべき条件を要件 ID つきのテストで残し、PC とスマホの画像を撮る。Claude は偽物に差し替える（D-87）。開発中に画面を見て確かめるときと、ランディングページ用の画像には Playwright（MCP）も使う | 画面の画像をダミーデータで撮り直せる。画面を変えるたびに、壊れにすぐ気づく |
| HK-CC-07 | ルール | `.claude/rules/`（C#・React・Biz のロジック・Claude API）でコーディング規約を守らせる（作成済み） | 1週間で書くコードの品質をそろえる |
| HK-CC-08 | モデルの使い分け | アプリ内では用途ごとにモデルを選ぶ（[02 の 9](02-functional.md#9-claude-の利用箇所まとめ)） | 精度・速さ・費用の釣り合いを取る |
| HK-CC-09 | レビューの基準 | `REVIEW.md` に、変えたものによるリスクの区分（高・中・低）、区分ごとのコミット前の手順、指摘の分け方（重要・細かい点・前からある）、往復を3回で打ち切る決まりを書く。同じ指摘が2回出たら決まりの方を直す（作成済み）。区分の判定とビルド・テスト・lint・E2E は `tools/precheck/precheck.py` でまとめて走らせ、通っていない差分のコミットはフック（HK-CC-02 と同じ `check-commit.py`）で止める（作成済み） | 人間が全部の差分を読まなくても、危ない変更にだけ注意を集められる。レビューの往復が終わらなくなるのを防ぐ |
| HK-CC-10 | CI | GitHub Actions で、main への push ごとにビルド・Biz のテスト・フロントの lint とビルドを走らせる（作成済み：`.github/workflows/ci.yml`） | 手元での確かめ忘れを拾う。審査員がテストの結果を見られる |

- 「開発者のいない現場の課題を、Claude Code 初心者が1週間で形にした」ことが伝わるように、要件定義から実装・テスト・デプロイまでで Claude Code をどう使ったかを README にまとめる

## 6. 試行錯誤の記録（HK-LOG）

優先度：**必須**

| ID | 要件 |
| --- | --- |
| HK-LOG-01 | 要件の決定の経緯は [07 の決定の記録](07-open-questions.md#3-決定の記録) に残し、README から案内する（例：ヘーゼルナッツの見落とし → 29品目外の品目と原材料全文の検索を追加） |
| HK-LOG-02 | チラシの読み取り精度を、ダミーのチラシで測る（何商品中、商品名・価格・アレルゲン表記を何件正しく読めたか）。プロンプトや画像の解像度を変えたら測り直し、結果を残す |
| HK-LOG-03 | 実物のチラシで「（乳）」を読み落とした記録（[02 の 3](02-functional.md#3-チラシ取り込みfr-flyer)）のように、Claude の誤りから設計を変えたことを残す |
