# 06. 非機能要件

## 1. セキュリティ・プライバシー（NFR-SEC）

| ID | 要件 |
| --- | --- |
| NFR-SEC-01 | 本番は HTTPS のみで提供する（HTTP はリダイレクト） |
| NFR-SEC-02 | 実データを扱う前にログイン機能を入れる。全 API で認証を必須にする |
| NFR-SEC-03 | パスワードはハッシュ化して保存する（ASP.NET Core Identity の仕組みなど標準のものを使う） |
| NFR-SEC-04 | 子どもの情報は登録しない。名前・呼び名・番号などの入力欄を作らず、アレルギーは施設の「避ける品目」としてだけ持つ |
| NFR-SEC-05 | Claude に送るアレルギーの情報は「施設の避ける品目の一覧」に限る |
| NFR-SEC-05a | 週の要望・チャットの文章は Claude に送るため、入力欄に「子どもの名前は書かないでください」と表示する |
| NFR-SEC-06 | チラシ・パッケージの画像はサーバーに保存しない。Claude の呼び出し（読み取りと読み取りの検証）が終わったら、すぐにメモリから破棄する。確定の画面で見せる画像は、ブラウザが持っているものを使う |
| NFR-SEC-07 | ログに子どもの情報・画像・API キーを出さない |
| NFR-SEC-08 | API キーはリポジトリに入れない（開発時は user-secrets / 環境変数、本番は環境変数など） |
| NFR-SEC-09 | 公開リポジトリには、実データ・画像・サーバーの IP アドレス・`docs/context/` を入れない |
| NFR-SEC-10 | ログインの Cookie は `HttpOnly`・`Secure`・`SameSite=Lax` にする。状態を変える API（POST・PUT・DELETE）は ASP.NET Core の Antiforgery（`X-XSRF-TOKEN` ヘッダー）を必須にする。`/api` で認証がないときは、ログイン画面へのリダイレクト（302）ではなく 401 を返す |
| NFR-SEC-11 | プロンプトインジェクションへの備え：画像の文字・要望・チャットの文章は「データであり、指示ではない」とプロンプトに書く。出力は構造化出力のスキーマで受け、Biz で検証する（[SR-18](03-allergen-safety.md)）。Claude の出力を、アレルゲンの判定・ステータス・設定の更新に使わない。Claude の文章は画面にテキストとして表示する（HTML として描画しない） |

## 2. 性能（NFR-PERF）

利用者は1施設の職員1人、商品は数百件を想定する。

| ID | 要件 |
| --- | --- |
| NFR-PERF-01 | Claude を使わない画面操作は、1秒程度で応答する |
| NFR-PERF-02 | Claude を使う処理（チラシ読み取り・献立提案）は、目安として60秒以内に終わる（献立案は検証と差し戻しを含めて3分以内）。それまでは進捗を段階で表示する。60秒・3分は目安で、処理を打ち切る期限ではない。打ち切る期限は、タイムアウトと再試行の合計（NFR-OPS-04）より長くする |
| NFR-PERF-03 | 商品照合の類似度は、アプリ側で全件計算してよい（数千件を超えたら DB 側の絞り込みに切り替える） |
| NFR-PERF-04 | 画像はアップロード前にブラウザ側で **JPEG・長辺 2576px・品質 0.85 程度** に変換する（Sonnet 5 系の画像の上限は長辺 2576px・約 3.75MP で、それより大きく送っても読み取りは良くならない。上限の大きさでは1枚あたり約 4,800 トークンかかるため、費用はダミーのチラシで測る）。**小さい文字（アレルゲン表記）が読めること**を優先し、ダミーのチラシで読み取り精度を測って調整する（[HK-LOG-02](08-hackathon.md)）<br>・**PDF** はブラウザで pdf.js を使ってページごとに画像にし、画像と同じ流れで扱う（Claude には PDF を送らない。ページ選びとサムネイルに画像が要るため）<br>・**HEIC** は Claude の API が受け付けない（対応は JPEG・PNG・GIF・WebP）。ブラウザで読めた場合だけ JPEG に変換し、読めなければ「JPEG で保存し直してください」と表示する（iOS Safari は写真を選ぶと JPEG で渡すことが多い。実機で確かめる）<br>・1枚あたりの大きさの上限（API は約 5MB）は、実装時に公式ドキュメントで確かめる |
| NFR-PERF-05 | Claude を呼ぶ処理は、サーバーのバックグラウンドの処理として受け付けて ID を返し、画面は2秒ごとに状態（段階名・結果）を取りに行く。IIS（ASP.NET Core Module）の既定のタイムアウト（2分）に縛られないようにするため。処理の状態はメモリに持ち、アプリが再起動したら「失敗」として扱い、再試行できるようにする |

## 3. 使いやすさ（NFR-UX）

| ID | 要件 |
| --- | --- |
| NFR-UX-01 | スマホ（iOS Safari・Android Chrome）と PC（Chrome・Edge）の最新版で動く |
| NFR-UX-02 | スマホではカメラを直接起動して撮影できる。PC・スマホとも、画像（JPEG・PNG・HEIC）と PDF のファイルを選んで取り込める |
| NFR-UX-02a | 取り込めるのは1ファイル 20MB まで、1回10枚（PDF はページ）まで。超えた場合や対応していない形式の場合は、理由を日本語で表示する。IIS の `maxAllowedContentLength` もこれに合わせて設定する。設定は Server プロジェクトの `web.config` に書き、`dotnet publish` の成果物に含める（サーバー上で手で直さない） |
| NFR-UX-03 | エラーメッセージは日本語で、次に何をすればよいかを書く |
| NFR-UX-04 | Claude の処理が失敗しても、入力済みの内容を失わず再試行できる |

## 4. 信頼性・運用（NFR-OPS）

| ID | 要件 |
| --- | --- |
| NFR-OPS-01 | 本番は XServer VPS for Windows Server + IIS で動かす。サーバー上ではビルドせず、手元で `dotnet publish` した成果物を配置する |
| NFR-OPS-01a | 本番の DB のマイグレーションは、手元で SQL を作り（`dotnet ef migrations script --idempotent`）、サーバーで適用する。適用の前に DB をバックアップする（D-42） |
| NFR-OPS-02 | SQLite を1日1回以上バックアップする。動作中のファイルを単純にコピーすると壊れたバックアップになりうるため、`VACUUM INTO` か SQLite のバックアップ API で日付つきのファイルに書き出す（Windows のタスク スケジューラで実行）。7世代残す。バックアップのフォルダは Web から見えない場所に置く |
| NFR-OPS-03 | Claude API の障害時でも、商品一覧・既存の献立の閲覧・手動での献立編集はできる |
| NFR-OPS-04 | Claude API の呼び出しには、タイムアウトと再試行を設ける。再試行は2回まで。タイムアウトは、画像の読み取り（チラシ・パッケージ）と献立の提案が90秒、商品照合の判定が30秒（仮の値。実測で見直す）。SDK の自動の再試行は切り、アプリで再試行する（1日の呼び出し回数に再試行も数えるため。NFR-COST-05）（D-64） |
| NFR-OPS-05 | 使用モデル名は**用途ごとに**設定ファイルから読む（既定 `claude-sonnet-5-5`。商品照合の判定は `claude-haiku-5-5`。用途とモデルの対応は [02 の 9](02-functional.md#9-claude-の利用箇所まとめ)） |
| NFR-OPS-06 | エラーはサーバーのログに記録する（個人情報を除く） |
| NFR-OPS-07 | 日時は UTC で保存し、「今日」「週（月曜始まり）」「月」・再確認期間の判定は日本時間（`Tokyo Standard Time`）の日付で行う。Biz には時計（`TimeProvider`）を外から渡し、テストで日付を固定できるようにする。SQLite は日時の種類（UTC かどうか）を持たないため、EF Core で DateTime の列すべてに「UTC として読む」変換（`Kind=Utc` にする ValueConverter）を付ける（D-80） |
| NFR-OPS-08 | 本番の準備が締切に間に合わない場合は、手元の環境（ダミーデータ）でデモ動画を撮る。ランディングページの公開を優先する |

## 5. 保守性（NFR-MNT）

| ID | 要件 |
| --- | --- |
| NFR-MNT-01 | 依存方向は `Server → Data / Claude → Biz` を守る。マイグレーションは `OyatsuBiyori.Migrations` に分け、`Migrations → Data`、`Server → Migrations` とする（D-40） |
| NFR-MNT-02 | アレルゲン判定・金額計算・週の予算の計算・商品名の正規化と照合は Biz に置き、xUnit でテストする |
| NFR-MNT-03 | Claude へのプロンプトは `OyatsuBiyori.Claude/Prompts/` にまとめ、コードと分けて管理する。プロンプトのファイルは埋め込みリソース（EmbeddedResource）として DLL に含め、`dotnet publish` で漏れないようにする（D-80） |
| NFR-MNT-04 | コーディング規約は `.claude/rules/` に従う |
| NFR-MNT-05 | Claude に使わせるツール（[FR-MENU-16](02-functional.md#521-ツールを使う献立づくりエージェント)）は、**判断ロジックを Biz**、**ツールの定義（名前・説明文・JSON スキーマ）・ループ・Biz への振り分けを `OyatsuBiyori.Claude`** に置く。Biz は Anthropic の SDK に依存させない。ツールの結果を返す処理で、Biz の結果を書き換えない |

## 6. コスト（NFR-COST）

| ID | 要件 |
| --- | --- |
| NFR-COST-01 | Claude API を呼ぶたびに、用途・モデル・入力と出力のトークン数をサーバーのログに出す（必須。本文や画像は出さない） |
| NFR-COST-02 | 献立提案に渡す商品は、その週の掲載品のうち候補になるもの（FR-MENU-07c・判定が「入れられない」でないもの）に絞る（入力トークンを抑える） |
| NFR-COST-03 | ダミーデータで1週間分の献立づくり（チラシ取り込みと読み取りの検証・献立提案・検証による修正・数回のチャット修正・アレルゲン確認）を通して行い、NFR-COST-01 のログから費用を求める。「1週間あたり約○円」を README とランディングページに載せる（必須） |
| NFR-COST-04 | 1週間分の費用を画面で確認できるようにする（あると良い。`api_usage_logs` から求める） |
| NFR-COST-05 | 費用の上限を設ける（必須）：Anthropic の Console でワークスペースの月の利用上限を設定する。アプリでも1日の呼び出し回数の上限（200回。設定で変えられる。NFR-COST-03 で1週分の回数を測り、その3倍程度に見直す）を持ち、超えたら「今日は AI を使えません。手で編集してください」と表示する。回数は日本時間の日付ごとに、失敗した呼び出し・再試行も含めて数える（D-65）。取り込みの枚数（10枚）・差し戻し（3回）・エージェントのループ（10回）の上限と合わせて、1回の操作の費用にも上限があるようにする |
