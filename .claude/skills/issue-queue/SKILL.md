# キューの issue を1件ずつサブエージェントで片付ける

`docs/context/issue-queue.md`（**キュー**。スキル `issue-triage` が作る）の上から、issue を1件ずつ片付ける。1件ごとに新しいサブエージェント `issue-worker`（以下「ワーカー」）を作り、計画・実装・確認（`precheck.py`）を任せる。メイン（この会話）は、ユーザーとのやりとり・レビュー・コミット・キューの更新を受け持つ。

- **1件ずつ、順番に**進める。ワーカーを同時に2つ動かさない（同じ作業ツリーで差分が混ざり、`precheck.py` の記録もコミットも分けられなくなるため）
- 1件 = 1回のコミット。次の issue は、前の issue をコミットするか、退避してから始める
- キューを書き換えるのはメインだけ（ワーカーには触らせない）
- **push はしない**。ユーザーに言われたときだけ行う（CLAUDE.md）

## 0. 準備

1. キューを読む。なければ `issue-triage` を先に実行する。最終トリアージから新しく起票された issue があれば（`gh issue list --state open --json number`）、トリアージし直すか聞く
2. `git status --short` を見る。作業中の差分があれば、**始めない**。キューの「作業中の差分」と照らし、どの issue の途中かをユーザーに伝えて、①その issue としてワーカーに続きを任せる ②先にコミットする ③退避する、のどれにするか聞く
3. **実行の設定**をユーザーに聞く（AskUserQuestion。前回の設定がキューにあれば、それを最初の選択肢にする）。決めたら、キューの「実行の設定」の節（なければ「作業中の差分」の前に足す）に日付つきで書く。この設定は、この実行の中でだけ有効

| 設定 | 選択肢 |
| --- | --- |
| 計画の承認 | **1件ずつ見る**（ワーカーの計画をユーザーに見せて OK をもらう）／ **キューの承認で代える**（下の「計画をメインで確かめる」に当たらなければ、そのまま実装へ進める） |
| コミット | **1件ずつ承認**（コミットの前に毎回聞く）／ **条件つきで自動**（下の「自動でコミットしてよいとき」をすべて満たすときだけ、聞かずにコミットする。満たさなければ止めて聞く） |
| どこまで | キューが空になるまで ／ <n> 件まで ／ <時刻> まで |

「条件つきで自動」を選んだことが、CLAUDE.md の「コミットはユーザーが指示したときだけ」の指示にあたる。設定にない操作（push、issue を閉じる以外の GitHub の操作など）は、この設定では許されない。

## 1. 次の issue を選ぶ

キューの上から、状態が `待ち` で、「先に要る」の issue がすべて `✅` のものを1件選ぶ。なければ 7. へ。

- キューのその行を `作業中` にし、「記録」に `<時刻> #<番号> 着手` を足す
- `gh issue view <番号>` で、issue が開いていることを確かめる（閉じていれば `✅ （GitHub で閉じた）` にして次へ）

## 2. ワーカーに計画を作らせる

`issue-worker` を新しく作る（Agent。`subagent_type: "issue-worker"`、名前は `issue-<番号>`）。渡すのは次のものだけにする（メインの考えを渡しすぎない。ワーカーが自分で issue と要件を読んで決めるため）。

- issue の番号とタイトル
- キューのその行（触るファイルの見込み・大きさ・先に要る issue）と、「順番の理由」のうちこの issue に関係するところ
- 「1回目：計画だけを返す」の段階であること

### 計画をメインで確かめる

返ってきた計画を、次の点で確かめる。1つでも当たれば、設定にかかわらずユーザーに見せて判断をもらう。

- 計画の「止める理由」が `⏸` になっている
- 触るファイルがキューの見込みから大きく外れている（別の画面・別の層にまで広がっている）、または issue の終わりの条件を超えたことをしようとしている
- 要件を変える、新しいプロジェクト・フォルダ・パッケージを足す、SR- に関わる判定を変える
- リスクの区分が高、または安全レビューが要る

「計画の承認：1件ずつ見る」なら、当たらなくても計画を見せて OK をもらう（`issue-run` の承認1と同じ中身）。直してほしいと言われたら、SendMessage でワーカーに伝え、計画を作り直させる。

`⏸` のときは 6. の「保留にする」へ。

## 3. 実装させる

SendMessage でワーカーに「計画どおりに実装して、確認まで進めて」と送る（ユーザーが計画に注文を付けたら、それも添える）。報告が返るまで待つ。待っている間に、同じ作業ツリーのファイルを変えない。

報告が `⏸` なら 6. の「保留にする」へ。

## 4. メインで確かめて、レビューする

ワーカーの報告をそのまま信じず、次を自分で見る。

1. `git status --short` と `git diff --stat`：変わったファイルが報告と同じで、issue の範囲に収まっているか。範囲外の変更があれば、ワーカーに戻させる
2. `python tools/precheck/precheck.py --dry-run`：区分を確かめる。報告と違えば、その理由を確かめる（中身が高なのに中と出ていれば、ワーカーに `--risk high` でやり直させる）
3. **レビュー**（区分が中・高のとき）：`/code-review` で差分を見る
4. **安全レビュー**（区分が高でアレルゲン・献立・Claude の出力に触れるとき。`安全レビュー` のラベルが付いた issue は必ず）：`allergen-safety-reviewer` に、issue の番号と終わりの条件、変えたファイルを渡す。ワーカーの計画や報告は渡さない（それに引っ張られずに見てもらうため）
5. **直させる**：指摘を REVIEW.md の「4. 指摘の分け方」で分け、「重要」と「細かい点」をまとめて SendMessage でワーカーに送る。直したら、1. からやり直す。往復は**3回まで**（2回目からは前回のレビュー後に変わった差分だけを見せる）。3回で残った指摘は、ユーザーに判断を仰ぐ。同じ種類の指摘が2回出たら、`CLAUDE.md`・`.claude/rules/`・`REVIEW.md` に書き足す案を出す
6. **終わりの条件**：報告のチェックを、差分と照らして1つずつ確かめる。満たしていないものがあれば、ワーカーに戻すか、状態を `🔶` にする（ユーザーに伝える）

ログイン・HTTPS・公開の設定に触れたら、デプロイ前に `/security-review` が要ることを、この issue のまとめに書く。

## 5. コミットする

### 自動でコミットしてよいとき

「コミット：条件つきで自動」のときは、次を**すべて**満たせば、聞かずにコミットしてよい。1つでも外れれば、`issue-run` の承認2と同じ中身を見せて、OK をもらってからコミットする。

- `precheck.py` が通っていて、そのあとに差分を変えていない
- レビューで「重要」が残っていない。「細かい点」はすべて直したか、理由を書いて閉じた
- 終わりの条件をすべて満たした（`🔶` でない）
- 区分が低か中で、`安全レビュー` のラベルが付いていない
- 職員が見て判断する文言・画面（アレルゲンの表示・確定の条件・警告の言葉など）を変えていない。見た目だけの変更（配置・色・余白）はよいが、E2E の画像のパスを、まとめ（7.）でユーザーに見せる。REVIEW.md の「職員が見て判断する文言・画面はユーザーに確認する」は、push の前にこれで果たす

### コミットのしかた

`issue-run` の「6. コミット」に従う（日本語のメッセージ、`Closes #<番号>`、高なら「確かめ方・リスク・戻し方」、Write で scratchpad に書いて `git commit -F`、会話で指定された Co-Authored-By の行、フックに止められたら直す）。メッセージは、ワーカーの案を元にメインで書き直す。

コミットしたら、キューのその行を `✅ <短いハッシュ>` にし、「記録」に `<時刻> #<番号> ✅ <ハッシュ>（レビュー<n>回、<残したこと>）` を足す。ワーカーの「気づいたこと」は、キューの「記録」に書き写しておく（起票はまとめ（7.）のあとにユーザーと決める）。

## 6. 保留にする・見送る

- **保留にする**（`⏸`）：ワーカーが止まった、レビューが3回で終わらない、ユーザーの判断が要る、など。キューのその行を `⏸ <理由>` にし、「決めてほしいこと」に問いを書く
  - 作業中の差分が残っていれば、`git stash push -u -m "issue-#<番号> の途中"` で退避し、キューの「記録」に退避したことを書く（差分を消さない。`git stash drop`・`git checkout --`・`git reset --hard` は使わない）
  - そのうえで、この issue を「先に要る」にしていない次の issue へ進む（1. へ）。ユーザーがその場にいて、すぐ答えられるなら、聞いてから決めてもよい
- **見送る**（`⏭`）：ユーザーが「やらない」と決めたときだけ。理由をキューに書く。issue を閉じるかどうかはユーザーに聞く

## 7. 止まる・まとめる

次のどれかで、ワーカーを作るのをやめて、まとめを伝える。

- 進められる issue がなくなった（すべて `✅`・`⏸`・`⏭`、または「先に要る」が終わっていない）
- 「どこまで」の設定に届いた
- ユーザーに聞いて止まっている（答えをもらったら続ける）
- ビルドや `precheck.py` が、issue と関係なく壊れている（次の issue でも同じことになるため。直し方をユーザーに相談する）

まとめに書くこと：

- 片付けた issue（番号・タイトル・コミットのハッシュ）
- 保留・見送りの issue と、決めてほしいこと（退避した差分があれば、その名前）
- ユーザーに見てほしい画面（E2E の画像のパス。PC とスマホ）
- ワーカーの「気づいたこと」（issue にするなら `brushup-issue` で起票する。案づくりを `issue-drafter` に任せてもよい）
- push していないこと。push するなら、CI（`.github/workflows/ci.yml`）の結果も確かめること
- キューの次の候補
