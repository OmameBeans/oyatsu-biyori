# 計算・判定ロジックの決まり（Biz）

金額・予算・アレルゲン・重複・商品照合のロジックは Biz に置き、xUnit でテストする。Claude の出力は信用せず、ここで計算し直す。
このファイルには間違えやすい点だけを書く。定義の正は要件定義なので、書く前に参照先を読む。

## 金額（[02 §5「金額計算の定義」](../../docs/requirements/02-functional.md)）

- パック数（`menu_items.pack_count`）は保存する値（D-43）。既定は式で求める：**切り上げ**（その日の人数 × 1人あたりの個数 ÷ 入数）。1人あたりの個数は既定1
  - 入れ替え案と職員は、パック数を上書きできる
  - その日の人数か1人あたりの個数を変えたら、式で求め直す
  - パック数 × 入数 が その日の人数 × 1人あたりの個数 に足りなければ、警告を出す（禁止はしない）
- 入数・1人あたりの個数は1以上の整数、税込価格は1以上の整数。入数0は計算の前に拒む
- 1人あたり金額は小数のまま計算し、**表示するときだけ**円未満を四捨五入する
- 献立の商品の金額は、献立に入れた時点の価格（`menu_items.unit_price`）で計算する。商品の最新の価格は使わない
- 手作り・おやつなしの日に商品があっても、その日の金額は0のままにする。「金額に含まれていません」の警告で知らせる（D-77）

## 予算（[02 §1「週の予算の扱い」](../../docs/requirements/02-functional.md)）

- 予算は週ごと。献立を作るときに既定の週の予算（`settings.default_weekly_budget`）を `menus.weekly_budget` に写し、職員が上書きできる。月の予算・月の実績は持たない
- 予算を超えても禁止しない。警告を出すだけにする

## 予算に合わせる入れ替え案（[02 §5.4](../../docs/requirements/02-functional.md)）

- 入れ替え案を出すのは、週の実績が週の予算に届かないときだけ（D-67）
- 探索はアプリ側で全通り試す。Claude に計算させない
- 目標額はその献立の週の予算（FR-MENU-27）。これを**超えない**範囲で、差が最も小さいものから上位3件。今の差より小さくならない案は出さない
- 試すのは「1か所の商品の入れ替え」「1日に1品の追加」「1か所のパック数 ±1」だけ（2か所以上の組み合わせは作らない）。同じ日にすでにある商品の追加は試さない
- 試すのは、日の種類が通常の日で、人数が1以上の日だけ（手作り・おやつなし・人数0の日は金額が0なので試さない。D-80）
- 候補から外すもの：03 §5 の判定が「入れられない」の商品（含む・含む可能性あり・不明）、税込価格か入数が未入力の商品、「対象外」の分類、「今週は使わない」にした商品、「使わない」商品。「参考」「要再確認」などの警告の商品は、警告の印を付けて候補にしてよい
- 候補は、その献立の掲載品の写し（`menus.listed_products`）から選ぶ

## 重複ルール（FR-COND-05、FR-MENU-12）

- 分類ごとの日数は `duplicate_avoid_days`（`{ 分類, 日数 }` の配列）で持つ。配列にない分類は制限なし
- 期間内の商品が入っても禁止しない。「○日前に出した」と警告する
- 比べるのは確定献立だけ。その日の日付から数え、同じ週の中の重複も警告する。Claude に渡す確定献立は、最も長い期間＋1週分（D-48）

## 献立案の検証（FR-MENU-15、[02 §5「確定」](../../docs/requirements/02-functional.md)）

Claude の案・手動の編集・チャット・入れ替え案のどれにも同じ検証をかける。

| 種類 | 内容 | 扱い |
| --- | --- | --- |
| エラー | 判定が「入れられない」の商品 / その週の掲載品にない商品 / 写しの税込価格か入数がない商品 / 存在しない商品 / 候補から外した商品（「今週は使わない」「使わない」「対象外」の分類。D-52） | Claude の案なら差し戻して直させる |
| 警告 | 判定が「警告」の商品 / 重複 / 予算超過 / 通常の日が0品 / 手作り・おやつなしの日に商品がある / 全員分に足りないパック数 | 表示だけ。確定は止めない（D-75・D-77） |

- 確定を止めるのは、入れられない商品・価格か入数がない商品・掲載品にない商品の3つだけ（D-78）。候補から外した商品は、確定では警告にする
- 警告の商品は、確定時に商品ごとの確認が要る（SR-04・SR-22）

## アレルゲンの判定（[03 §5](../../docs/requirements/03-allergen-safety.md)）

- 「含む」品目と原材料の全文は、最新の記録1件ではなく「有効な記録」（最新の確認済みと、それより後のすべての記録）から求める。参考の記録で「含む」が減らないようにする
- 探す言葉・商品名・全文は同じ正規化（NFKC → カタカナをひらがなに → 空白・改行・記号の除去）をしてから部分一致で探す。商品照合用の正規化（「コープ」の除去あり）や `normalized_name` は使わない
- 探す言葉の正規化は、正規化したあとの位置を元の文字列の範囲に戻す対応も返す（当たった言葉を全文の上で強調するため）。改行・全角・カタカナをまたいで当たった場合も、元の範囲に戻せるようにする
- 判定の順序は 03 §5 の疑似コードどおりにする。**ステータスより先に「含む」「含む可能性あり」を調べる**。結果は「入れられない（エラー）/ 警告 / 安全」の3つに分け、どの条件にも当たらないときだけ「安全」にする
- 「要再確認」は保存しない。最新の「確認済み」の記録の確認日から、表示のたびに求める。`今日 - 確認日 > 再確認期間` で要再確認（90日なら、90日目までは期限内、91日目から要再確認）
- 判定に使う「今日」は引数か `TimeProvider` で受け取る（境界をテストできるように。`DateTime.Now` を直接使わない）
- 避ける品目の「探す言葉」は、商品名と原材料の全文（`raw_ingredients_ocr`・`raw_ingredients` の両方）を正規化してから探す（全角・半角、カタカナ・ひらがなの違いで見落とさない）。ステータスや職員の確定にかかわらず、見つかったら「含む可能性あり」（入れられない）にする（SR-14）
- 「確認済み」の記録がある商品には、チラシから「参考」の記録を追加しない。チラシの表記との食い違いは SR-20 のとおり扱う
- 避ける品目に「表示が確実でない」品目（推奨20品目・経過措置中のカシューナッツ。マスタの印で判断し、コードに品目を直書きしない）があるときは、「安全」でも「メーカーへの確認が必要」を付ける

## 商品名の正規化と照合（[02 §3.1](../../docs/requirements/02-functional.md)）

- 正規化は、保存するときと検索するときで**同じ関数**を使う：NFKC → カタカナをひらがなに → 「CO・OP」「コープ」の除去 → 記号・空白の除去
- 内容量も正規化してから比べる：NFKC → 空白の除去 → 「×」「x」「＊」と括弧の書き方をそろえる（「40g（2袋×12個包装）」と「40g(2袋x12個包装)」を同じにする）
- ルールで決められるものは機械的に決め、迷うものだけ Claude（Haiku）に回す（D-63）
  1. 正規化名と正規化した内容量が一致（メーカーは両方に値があるときだけ比べる）→「同じ商品」の候補
  2. 正規化名が同じで内容量が違う →「内容量違い」
  3. それ以外は文字バイグラムの Dice 係数で上位5件、しきい値 0.3（設定で変えられるようにする）。似ているが一致しない商品を「Claude に回すもの」として返す。全件をアプリ側で計算してよい
- 形態素解析・ベクトル検索は使わない
- 迷う場合は別商品として扱う。「味違い」「内容量違い」の商品にはアレルゲン確認を引き継がない（SR-05）
- 同じチラシの中の二重も、正規化名と正規化した内容量で見つける

## テスト（Biz.Tests）

- 03 §5「テストで必ず確かめること」の項目は、すべてテストにする（ヘーゼルナッツの事例、90日・91日の境界、最新の記録が「参考」なら古い「確認済み」より優先される、など）
- 金額の切り上げ・切り捨てには、境界のテストを書く
- テストデータはダミーだけを使う（架空の商品名）。人数は現場の規模（40〜70人）に合わせる
