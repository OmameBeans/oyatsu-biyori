# おやつ日和（oyatsu-biyori）

**チラシを撮るだけで、1週間分のおやつ献立案。** 学童保育の職員のための、おやつ献立アシスタントです。

生協（コープ）のチラシを撮影（または画像・PDF を選ぶ）すると、載っている商品を読み取り、施設の条件（人数・週の予算・避ける品目・同じおやつを続けない期間）と、職員が文章で伝えた週の要望から、Claude が**理由つきの献立案**を作ります。職員はチャットで直したり、手で入れ替えたりして確定します。

「Built with Claude: Japan 2026」（テーマ1「あなたにしかない深さを」）の提出作品です。

## 誰の・どんな課題を・どう解決するか

- **誰の**：学童保育の職員（1つの施設・1つのアカウント。PC とスマホの両方から使う）
- **どんな課題**：毎週、チラシとにらめっこして1〜2時間。予算・人数・行事・アレルギー・同じおやつが続かないか……と条件が多く、保育の合間に「気が抜けない」作業をしている。とくにアレルゲンは、29品目に入らない食材（ヘーゼルナッツなど）を見落とした例が現場で実際にあった
- **どう解決するか**：読み取り・照合・献立の組み立て・理由の説明は Claude に任せ、**アレルギー・予算・人数の条件はアプリが必ずチェック**する。最後の確認は職員がパッケージで行う。現場の職員の判断の深さ（どこで見落としが起きるか）を、判定のルールと画面の流れに落とし込んだ（テーマ1）

## 使い方（4ステップ）

1. **撮る**：献立一覧で週を選び、チラシを撮る。商品・価格・注文番号・アレルゲンの表記を読み取り、登録済みの商品と「同じ商品かどうか」を調べる。職員が1件ずつ（完全一致はまとめて）確定する
2. **確かめる**：今週の商品を一覧で見渡す。アレルゲンの表示（🔴 使えません / 🟡 要確認 / 🟢 使えます）と理由、何日前に出したか、が並ぶ
3. **伝える**：「金曜は誕生日会なので豪華に」「水曜は子どもが30人」などの要望を文章で伝えて「献立を作る」
4. **直す**：日ごとの献立案と理由を見て、チャットで直す・手で入れ替える・「予算に合わせる」入れ替え案を選ぶ。確定のときは、🟡 の商品を1件ずつ確かめる

届いた商品はパッケージの原材料表示を撮って確かめ、記録します（アレルゲン確認）。その結果 🔴 になった商品が今日以降の献立にあれば、献立一覧の最上部と日ごとのカードに警告が出ます。

## 安全への考え方

子どもの安全に関わるため、迷ったら「確認する側」に倒します。詳しくは [docs/requirements/03-allergen-safety.md](docs/requirements/03-allergen-safety.md)。

- **判定はアプリ（Biz）が行い、Claude には任せない**。Claude の出した献立案は必ずアプリが検証し、問題があれば差し戻す。直しきれなかった商品は外して示す
- 判定は「🔴 入れられない / 🟡 警告（確認すれば確定できる）/ 🟢 安全」の3つ。「**不明」は避ける品目が1つでもあれば 🔴**、チラシなどの「参考」は 🟡 で、🟢 にはならない
- **探す言葉は、商品名と原材料の全文の両方で探す**（全角・半角、カタカナ・ひらがな、改行をまたいでも見落とさない）。職員が「含まない」にしても、当たった言葉があれば 🔴 のまま
- 「確認済み」にできるのは、職員がパッケージを見て、原材料の全文と、29品目と避ける追加品目のすべてを決めたときだけ。確認の記録は**追加のみ**（DB のトリガーでも書き換え・削除を止める）。一定期間（既定90日）を過ぎると要再確認に戻る
- 確定のときの確認は「理由と次にすること」を含む1文にチェックする（「チラシの情報だけです。届いたらパッケージで確認します」）。確認したときの判定と今の判定が違えば、確認し直しになる
- 要望・チャットの文章で、アレルギー・予算・重複の期間の条件は緩められない。子どもの情報は登録しない（施設の「避ける品目」だけを持つ）

## 画面

| 画面 | できること |
| --- | --- |
| ランディング（`/`） | ログイン不要。実データは出さない |
| ログイン・パスワード変更 | 初期パスワードのままでは、ほかの画面に進めない |
| 献立一覧（ログイン直後） | 週ごとの状態・実績と予算・🔴/🟡/確認し直しのバッジ、対応が必要なこと |
| 献立作成（手順1〜4） | チラシ取り込み → 今週の商品 → 要望 → 献立案とチャット・確定 |
| 商品一覧・商品詳細 | 検索・アレルゲンの表示での絞り込み、基本情報・タグ・メモの編集、確認の履歴 |
| アレルゲン確認 | パッケージを撮る → 全文の読み取り → 品目ごとに決めて記録 |
| 設定 | 条件設定・避ける品目（グループ・探す言葉・施設で追加した品目）・パスワード変更 |

画面の画像は、ダミーデータの環境で `src/oyatsubiyori.client` の `npm run e2e` を走らせると `e2e/screenshots/` に PC とスマホの両方で撮られます（公開リポジトリには画像を入れない決まりのため、ここには載せていません）。

## 技術構成

- フロント：React 19 + TypeScript（Vite）、MUI、TanStack Query、react-router、pdf.js（PDF をページごとの画像にする）
- API：ASP.NET Core（.NET 10）、EF Core（SQLite）、ASP.NET Core Identity（Cookie・Antiforgery・ロック）
- Claude：公式 C# SDK（NuGet の `Anthropic`）。用途ごとにモデルを設定から読む

| 用途 | モデル | 呼び方 |
| --- | --- | --- |
| チラシの読み取り・読み取りの検証 | `claude-sonnet-5-5` | 画像入力＋構造化出力（検証は別の呼び出しで、疑わしい箇所だけを返させる） |
| 商品照合の判定 | `claude-haiku-5-5` | アプリのルール（正規化・完全一致・内容量違い・Dice 係数）で決まらない「迷うもの」だけ |
| 献立づくり（作成・チャット） | `claude-sonnet-5-5` | 手書きのエージェントのループ（10回まで）。道具（候補を探す・金額・重複・検証・提出）の判断ロジックは Biz に置き、`submit_menu` が検証を通ったら止める |
| 予算に合わせる案 | `claude-sonnet-5-5` | アプリが全通り計算した候補から、番号を選んで説明させるだけ |
| 原材料表示の読み取り | `claude-sonnet-5-5` | 画像入力＋構造化出力。結果は候補で、確定は職員 |

フォルダ構成と依存の向きは [CLAUDE.md](CLAUDE.md) を参照（`Server → Data / Claude → Biz`）。判定・計算のロジックはすべて Biz にあり、xUnit で確かめています。

## 起動方法（開発）

前提：.NET 10 SDK、Node.js、`dotnet dev-certs https --trust`

```
# 初期アカウントと API キー（リポジトリには入れない）
#   初期アカウントは、アカウントが1つもない DB で起動したときだけ作られる。
#   すでにアカウントがあれば、あとから user-secrets を変えても使われない（DB を作り直す：下の --reset-demo）
dotnet user-secrets set "Auth:InitialUserName" "<ユーザー名>" --project src/OyatsuBiyori.Server
dotnet user-secrets set "Auth:InitialPassword" "<初期パスワード>" --project src/OyatsuBiyori.Server
dotnet user-secrets set "Claude:ApiKey" "<Anthropic の API キー>" --project src/OyatsuBiyori.Server

# ダミーデータを入れる（開発の DB を作り直す）
#   Bash の場合
ASPNETCORE_ENVIRONMENT=Development dotnet run --project src/OyatsuBiyori.Server --no-launch-profile -- --reset-demo
#   PowerShell の場合
$env:ASPNETCORE_ENVIRONMENT = "Development"; dotnet run --project src/OyatsuBiyori.Server --no-launch-profile -- --reset-demo

# 起動（Vite も自動で起動する）
dotnet run --project src/OyatsuBiyori.Server
```

- テスト：`dotnet test src/OyatsuBiyori.Biz.Tests`（xUnit）、`cd src/oyatsubiyori.client && npm run e2e`（Playwright。Claude は偽物に差し替え、毎回作り直す SQLite とダミーデータで動く。手順は [e2e/README.md](src/oyatsubiyori.client/e2e/README.md)）
- 読み取り精度の測定（T3-11）：API キーを設定してから `$env:ASPNETCORE_ENVIRONMENT = "Development"; dotnet run --project src/OyatsuBiyori.Server --no-launch-profile -- --measure-reading --out <結果のファイル>.md`。架空のチラシ・パッケージ（`samples/`）を本物の Claude で読み取り、正解データと比べた表と、使ったトークン数を出す（環境を `E2E` にすると、偽の Claude で比べるコードだけを確かめる）
- コミット前の確認：`python tools/precheck/precheck.py`（変更のリスクの区分を決め、ビルド・テスト・lint・E2E のうち必要なものを走らせる）
- 本番の成果物：`dotnet publish src/OyatsuBiyori.Server -c Release`（本番では `DataProtection:KeysPath` を Web から見えない場所に必ず設定する）

## 1週間あたりの API 費用

**約50〜60円**（架空のチラシ20商品で、チラシの取り込み → 献立案 → チャット2回 → 予算に合わせる案 → 原材料表示の読み取り2件を本物の Claude で通した、2026-11-04 に2回測った。17〜18回の呼び出しで約 $0.32〜$0.37。単価は同日の公式の料金表（Sonnet 5.5：入力 $2・出力 $10・キャッシュの読み込み $0.10、Haiku 5.5：入力 $0.10・出力 $0.50。いずれも100万トークンあたり）、1ドル＝160円として計算）。実際のチラシは商品が多いので、多めに見て1週間あたり約100円です（実際のチラシでの実測は試用のときに行う。T7-04）。読み取りは1回のチラシで2回（読み取りと検証）、照合の判定は迷う商品だけ、献立づくりはループの回数だけ呼び出します。1日の呼び出しの上限（既定200回）を設け、失敗・再試行も含めて数えています。

## Claude Code の使い方

このアプリは Claude Code で開発しています。何のために何を使ったか：

- **要件を先に固める**：要件定義（`docs/requirements/`、要件 ID つき）と実装タスク（`docs/implementation-tasks/`）を先に作り、上位モデルのレビューと、要件ファイルごとのエージェントでの突き合わせで抜けを補った
- **決まりをファイルにする**：`CLAUDE.md` と `.claude/rules/`（C#・React・Claude の呼び出し・計算と判定のロジック）。同じ種類の指摘が2回出たら、決まりの方に書き足す（`REVIEW.md`）
- **フックで止める**：コミットの前に、公開してはいけないもの（`docs/context/`・DB・`samples/` 以外の画像・API キー・IP アドレス）と、確認していない差分を止める。Biz の `.cs` を編集するたびに xUnit を走らせる
- **リスクで確かめ方を変える**：`tools/precheck/precheck.py` が変更の場所から区分（高・中・低）を決め、ビルド・テスト・lint・E2E を走らせる
- **安全のレビューを専用のエージェントにする**：`.claude/agents/allergen-safety-reviewer.md`（SR-01〜22 と照らし合わせる）。レビューは上位モデル（Claude Fable 5.1）に advisor として頼み、2回目は直した差分だけを見て、新しい指摘は別のエージェントが反証を試みてから採用した
- **画面は E2E で確かめる**：判定・計算はクライアントに置かず、画面は要件 ID つきの Playwright のテストで PC とスマホの両方を確かめる
- **デモ環境の作り直しを Skill にする**：`.claude/skills/reset-demo/`

## データについて

`samples/` の商品・メーカー・生協の名前、価格、原材料はすべて架空で、実在の商品・企業・団体とは関係ありません。実際のチラシ・パッケージの画像や、子どもの情報はリポジトリに入れません。
