# ブラッシュアップの起票

ファーストの完成（第8回まで）のあとの改善は、GitHub の issue で管理する。issue が本体で、`docs/implementation-tasks/implementation-tasks.md` の「13. ブラッシュアップ（issue）」の表は、一覧と進み具合の記録になる。このスキルは**起票だけ**を扱う（実装・コミット・issue を閉じるのは、ふだんの開発の進め方と REVIEW.md に従う）。

## いちばん大事なこと：issue は公開される

リポジトリは公開なので、issue のタイトル・本文・コメントは誰でも読める。一度投稿すると、消してもキャッシュや通知メールに残りうる。だから次のものは issue に**書かない**（CLAUDE.md「公開リポジトリのルール」と同じ）。

- 子ども・職員・施設が特定できること（名前、人数と行事の組み合わせなど）
- 実際の商品名・メーカー名・価格（「〇〇社の△△ゼリー」ではなく「ゼリー系の商品」「ダミーデータの商品」と書く）
- チラシ・パッケージ・画面の画像（画面の画像も、実データが映りうるので貼らない。必要なら「ダミーデータの環境で」と状況を言葉で書く）
- API キー、パスワード、サーバーや自宅の IP アドレス、`docs/context/` の中身

ユーザーの話にこれらが混ざっていたら、言い換えた案を作り、「公開されるので、ここをこう言い換えました」と伝える。迷ったら書かない側に倒す。スクリプトも IP・API キー・画像の添付を機械的に止めるが、商品名や子どもの情報は機械では見分けられないので、目で確かめるのはこちらの役目。

## 起票の手順

### 案づくりをエージェントに任せるとき

手順1〜4（案づくり）は、エージェント `issue-drafter` に任せられる。実装の途中で気づいたことを、作業を止めずに issue にしたいとき（バックグラウンドで動かす）や、複数の案件をまとめて起票するときに向く。1件の小さな話で中身がもう分かっているなら、自分でやった方が早い。

- 呼ぶとき：ユーザーの言葉をそのまま渡し、分かっている状況（どの画面か、今何の作業中か）と、本文を書くフォルダ（scratchpad）を指定する
- エージェントは起票しない。返ってきた案は、手順5（起票の前に自分で確かめる）から続ける。「確かめたいこと」があれば、先にユーザーに聞く
- 返ってきた案もそのまま信じず、公開してはいけないものが本文にないかは、起票の前に自分の目でも確かめる

### 1. 話を聞いて、案件に分ける

ユーザーの話から「何が困るか・どうなってほしいか」をつかむ。足りなければ短く聞く（どの画面か、スマホか PC か、毎回起きるか）。

- **1つの issue は、1回のコミットで閉じられる大きさ**にする。話に複数の直したいことが混ざっていたら分けて、それぞれの案を作る
- 同じ件がないか確かめる：`gh issue list --state all --search "<言葉>"`。あれば新しく作らず、その issue を伝える（追記したいことがあればコメントの案を出す）

### 2. 関係する要件・コードを調べる

ラベルと「終わりの条件」を当て推量で決めないため、短く調べる。

- 要件 ID：`docs/requirements/` を grep して、関係する `FR-`・`SR-`・`NFR-`・画面 `SC-xx` を見つける。ファーストのタスク（`T9-03` など、implementation-tasks.md の 9 の「あると良い」）に当たるなら、その ID も書く
- 触りそうなファイル：`src/` を grep して見当をつける。リスクの区分は、このファイルで決まる（次の 3）
- **要件を変える話**（要件にない機能、要件と違う動き）なら、本文の「メモ」にそう書く。特に `03-allergen-safety.md`（SR-）を緩める方向の話は、issue にする前にユーザーに「安全要件を変えることになる」と伝える。要望で安全の判定を緩めないのがこのアプリの前提なので

### 3. ラベルを決める

4つの軸で決める。種類・優先度・リスクは1つずつ、安全レビューは当てはまるときだけ。

| 軸 | ラベル | 決め方 |
| --- | --- | --- |
| 種類 | `種類: 不具合` / `種類: 改善` / `種類: 見た目・文言` / `種類: ドキュメント` | 要件どおりに動かない → 不具合。動くが使いにくい・足りない → 改善。動作を変えない表示・言葉 → 見た目・文言 |
| 優先度 | `優先度: 必須` / `優先度: あると良い` / `優先度: 余裕があれば` | 締切（2026-11-08 20:00）までに直さないと、試用・デモ・提出に困るものが「必須」。子どもの安全に関わる不具合は必ず「必須」 |
| リスク | `リスク: 高` / `リスク: 中` / `リスク: 低` | **REVIEW.md の「1. リスクの区分」の表**で、触りそうなファイルから決める。これは見込みで、コミット前に `precheck.py` が実際の差分で決め直す。迷ったら高い方 |
| 安全レビュー | `安全レビュー` | アレルゲンの判定・確認の記録・献立の検証や確定の条件・Claude の出力の扱いに触れるもの。コミット前に `allergen-safety-reviewer` を使う印。**付けるならリスクは必ず「高」**（REVIEW.md でそう決まっているため。スクリプトも止める） |

「見た目・文言」でも、アレルゲンの表示（🔴🟡🟢・理由・「メーカーへの確認が必要」）の言葉を変えるものは、職員の判断を変えうるので「安全レビュー」と「リスク: 高」にする。

### 4. 本文を書く

タイトルは「何を・どうする」が分かる日本語の1文（例：「献立一覧で商品名から週を探せるようにする」）。本文は次の形で、scratchpad のファイルに Write ツールで書く（Bash のヒアドキュメントは日本語の長文で失敗しやすい）。

```markdown
## 何を直すか

（今どうなっていて、どうなってほしいか。職員がどの画面で何をするときの話か）

## きっかけ

（気づいた場面。試用・デモの準備・自分で触って、など。実データは言い換える）

## 終わりの条件

- [ ] （確かめられる形で。例：「スマホ幅で横スクロールが出ない」「E2E に FR-LIST-02 のテストがある」）
- [ ] （ロジックを変えるなら「xUnit のテストがある」、画面を変えるなら「E2E がある」を入れる）

## 関係する要件・タスク

（FR-LIST-02、SC-11、T9-03 など。なければ「なし（要件にない改善）」）

## リスクと確かめ方

- リスク：中（見込み。触りそうなファイル：`src/oyatsubiyori.client/src/pages/...`）
- 確かめ方：precheck.py → /code-review（高なら allergen-safety-reviewer も）

## メモ

（要件を変える話か、ほかの issue との関係、決めていないこと）
```

「終わりの条件」は、あとで閉じるときに満たしたかを判断する基準になる。あいまいな言葉（「いい感じに」「分かりやすく」）だけで終わらせず、何を見れば終わりと言えるかを書く。

### 5. 起票の前に自分で確かめる

起票してよいかをユーザーに聞く必要はない（ユーザーがそう決めた）。案ができたら、そのまま手順6で起票する。ただし、投稿の前に次を自分で確かめる。

- 公開してはいけないもの（上の「いちばん大事なこと」）が、タイトル・本文にないか。目で読む
- `--dry-run` を付けて実行し、チェックを通るか

次のときだけは、起票の前にユーザーに聞く。

- 安全要件（SR-）を緩める方向の話（手順2）
- 話が足りず、何を直すかが決められないとき（どの画面か分からない、など）。分からないところを推測で埋めて起票しない
- 公開してよいか迷うものが残るとき（言い換えでは消しきれないとき）

### 6. 起票する

```
python .claude/skills/brushup-issue/scripts/create_issue.py \
  --title "献立一覧で商品名から週を探せるようにする" \
  --body-file "<scratchpad>/issue-body.md" \
  --kind 改善 --priority あると良い --risk 中 \
  --refs "FR-LIST-02, SC-11, T9-03"
```

- `--safety` を付けると「安全レビュー」のラベルが付く（`--risk 高` が必要）
- スクリプトは、チェック → `gh issue create` → implementation-tasks.md の 13. の表に1行足す → タスクの HTML の作り直し、までを行う
- チェックで止まったら、理由を読んで本文を直す。チェックを外して通そうとしない（止まるのは公開してはいけないものがあるときなので）

### 7. 伝える

起票した issue の番号と URL を一覧で伝える。あわせて、タイトル・ラベル（4軸）・関係する要件・「終わりの条件」、公開に向けて言い換えたところを短く伝える（起票の前に見せていないので、直したいところがあればユーザーが issue を直せるように）。implementation-tasks.md と index.html が変わったことも伝える（コミットはユーザーの指示があってから。ドキュメントだけなのでリスクは「低」）。

## 表の「状態」の書き方（参考）

13. の表の「状態」は、起票のときは空欄。閉じるときは、ふだんの進み具合の記録と同じく `✅ <コミット>`、途中なら `🔶 <残り>` と書き、同じコミットに入れる。コミットのメッセージに `Closes #<番号>` を入れると、push で issue が閉じる。
